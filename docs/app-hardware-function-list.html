App-硬件联调说明

本文以当前 evt 分支实际代码为准，说明 App 在 EVT 阶段如何发现、连接、订阅、认证、读取设备状态、控制设备录音、导入设备文件和回连设备。目标读者是 App 开发、固件开发、测试与现场联调人员。

1. EVT 范围和结论

本构建只开放十个 EVT 业务命令：0x01、0x02、0x05、0x06、0x07、0x09、0x11、0x21、0x22、0x23。功能不在此集合内，即使固件广播了对应特征，App 也不会把它当作 EVT 能力使用。

App 已做

兼容扫描、GATT 合约校验、9 个必需 CCC、V1 认证、设备状态/配置、录音控制、文件列表与断点下载、前台自动回连、Debug 日志。

固件必须配合

严格广播身份、完整 GATT 属性、每个接口从正确特征返回正确的业务帧、可靠的 Indicate/Notify 以及固定字段长度和小端序。

明确不在 EVT

V2 Ticket/Proof 认证、FA18 实时音频、0x26 文件元数据和归档、OTA/WQOTA、云端票据、云端归档、Factory/UART。

联调判断原则：GATT 写成功只代表手机把数据交给系统蓝牙栈，不代表设备已执行。页面只有收到并验证设备的 Indicate/Notify 业务响应后，才把操作写成成功。

2. 整体通信架构

01用户界面查找设备、连接、认证、录音、导入文件。
02业务控制器校验当前会话、按钮状态、权限和超时策略。
03协议仓库组帧、解析、字段校验、命令与回包关联。
04BLE 传输层扫描、连接、服务发现、Read、Write、CCC 订阅、MTU。
05设备固件广播、GATT、执行命令、Indicate 或 Notify 回传结果。
用户点击“开始录音”
  -> App 检查：已连接 + 已认证 + FA17 已订阅 + 录音授权
  -> App 向 FA17 写入：ED | Length | 07 | 01 | CRC16
  -> 固件执行录音动作
  -> 固件从 FA17 Indicate：ED | Length | 87 | RecordState | CRC16
  -> App 校验 CRC、CMD、端点、字段长度
  -> 页面更新为“正在录音”

Indicate 的链路层确认由 Android/iOS 系统蓝牙栈完成；App 不另发业务 ACK。文件流使用 Notify，设备需要按 App 的接收速度和 ATT MTU 合理分包。

3. 设备广播和扫描

用户进入设备页后点击“查找附近设备”。当前 EVT 调试构建暂时关闭严格广播过滤：只要蓝牙设备有名称，就会显示在列表；没有名称的设备仍不显示。用户手动点击连接后，App 仍会严格校验 GATT 服务、特征 UUID 和属性，不符合 EVT GATT 合约的设备无法进入认证或控制流程。

下表是固件应遵守的正式 EVT 广播规范，也是自动回连仍会使用的身份匹配规则；它目前不是手动扫描列表的拦截条件。固件广播字段稳定后，可把 App 的兼容扫描开关重新切回严格模式。

广播字段固件 EVT V1.5 要求App 如何检查不满足时
本地名称AIPIN_XXXX，XXXX 是 4 位大写十六进制。当前手动扫描只要求“名称非空”；该格式用于正式身份识别和自动回连。手动扫描仍显示；自动回连不匹配。
Manufacturer Data恰好 8 字节：A3 89 + BtAddressRaw[6]。当前手动扫描不拦截；正式身份识别检查前两字节和总长度。手动扫描仍显示；自动回连不匹配。
名称和地址关联名称末四位必须等于 BtAddressRaw 最后两个字节拼接成的大写十六进制。例如原始地址末两字节为 12 34，名称应为 AIPIN_1234。手动扫描仍显示；自动回连不匹配。
服务 UUID广播或 Scan Response 中包含 0000AF30-0000-1000-8000-00805F9B34FB。当前手动扫描不拦截；正式身份识别接受完整 UUID 或短 UUID AF30。手动扫描仍显示；自动回连不匹配。

Android 扫描结果合并

部分 Android 手机把名称、厂商数据和 Service UUID 分散在广告包和 Scan Response 两次回调中。App 以同一平台设备 ID 为键，在 5 秒窗口内合并最近字段后再过滤，不会因为单次回调缺字段而误删真实设备。

列表实时性

同一设备只保留一条记录，新广播刷新 RSSI 和发现时间；5 秒没有新的广播，条目自动从列表移除。这样已关机、离开范围或停止广播的设备不会长期留在列表。

设备标识说明：Android 的 connectionId 通常是 MAC，iOS 则是 CoreBluetooth UUID，不能把 iOS 的 ID 当物理 MAC。跨平台回连使用厂商数据中 BtAddressRaw[6] 解析出的物理地址作为优先匹配依据。

4. EVT 订阅了哪些特征值

结论：GATT 服务发现和属性校验通过后，App 会在用户点击“认证设备”或“首次绑定设备”之前，按固定顺序建立 9 个必需 CCC 订阅；然后尝试建立 1 个可选 CCC 订阅。其中 FF13 是唯一 Notify 通道，其余均使用 Indicate。

App 不直接写 0x2902 描述符，而是调用原生 BLE SDK 的订阅接口。SDK 根据特征属性配置 CCC，App 再等待原生确认，最长 8 秒，并额外等待 16ms 让 Dart 监听器稳定后才允许发送能立即回包的业务命令。

固件特别注意：这 9 个 Indicate 特征应只暴露 Indicate，不要同时暴露 Notify。当前 Android 原生 BLE 插件遇到一个特征同时具有 Notify 和 Indicate 时会优先按 Notify 订阅，可能与 EVT 协议的 Indicate 预期不一致。FF13 则只应暴露 Notify。

响应路由规则：App 会同时检查“这条数据来自哪个特征”和“业务 CMD 是什么”。例如 0x89 只能从 FA19 进入认证流程，0xA2 只能从 FF12 进入文件列表流程。CRC 正确但来自错误特征的帧也会丢弃并写入日志，防止串包被误判为成功。

5. 从查找设备到可操作设备的完整流程

01扫描用户点击查找；当前显示所有有名称设备；列表实时过期。
02连接用户选中设备后连接，连接超时 15 秒。
03服务发现读取 GATT，校验 9 个必需端点与属性，超时 15 秒。
04CCC 准备按固定顺序开 9 个必需订阅，再尝试 FF11；每个最多 8 秒。
05认证通道就绪此时只允许用户认证、绑定；尚不允许读写受保护能力。
06V1 认证用户输入安全码，FA19 写 0x09，等待 0x89。
07MTU认证成功后请求 517，必须得到 ATT MTU ≥ 136。
08基础信息FA11 写 0x01，收到 0x81，必须是 ProtocolVersion=3。
09基线配置FA12 写 0x02，收到 0x82=1。
10详情刷新读取状态、电量、存储、设备时间、隐私时长和可选文件数，进入可操作状态。

6. 业务帧与接口映射

6.1 公共帧格式

Byte 0       : Header = 0xED
Byte 1..2    : Length = u16 Little-Endian
Byte 3       : CMD
Byte 4..N    : Content
Last 2 bytes : CRC16 = u16 Little-Endian

Length = CMD(1) + Content(N) + CRC16(2) = N + 3
CRC 算法 = CRC-16/CCITT-FALSE
poly=0x1021, init=0xFFFF, refin=false, refout=false, xorout=0x0000
CRC 覆盖范围 = CMD + Content；线上 CRC 低字节在前。

所有 u16、u32 均为小端序。App 会校验帧头、Length、CRC、CMD、端点、字段长度和枚举取值；任何校验失败都不会覆盖上一次有效设备状态。

接口App 发起方式固件回包位置用途和关键字段
0x01 → 0x81FA11 Write，Content 为空。FA11 Indicate设备信息。App 要求 ProtocolVersion=3；解析设备码、软硬件版本、名称、总/剩余存储、录音状态、电量和充电字段。
0x02 → 0x82FA12 Write，Content 固定 12 字节。FA12 Indicate认证后的基础配置。0x82 Content 仅 1 字节，只有 01 才成功。设备 UTC 使用 FA12 的 GATT Read 读取 0x82 + u32 UTC，不是空 Content 的 0x02 写入。
0x05 → 0x85FA15 GATT Read，不发送业务 Write。Read 返回业务帧；也接收 FA15 Indicate存储空间：TotalMB:u32LE + FreeMB:u32LE。
0x06 → 0x86FA16 WriteFA16 Indicate状态、录音授权、默认隐私时长。见下一小节的 SubCmd。
0x07 → 0x87FA17 Write，Content 为 Action。FA17 Indicate录音控制。0停止、1开始、2暂停、3恢复。
0x09 → 0x89FA19 Write，Content 为 Action + SecurityCode[6]。FA19 Indicate只实现 V1 六字节认证码。Action 0认证、1首次绑定、2恢复初始认证码；0x89 的 01 成功、00失败。
0x11 → 0x91FB11 GATT Read，不发送业务 Write。Read 返回业务帧；也接收 FB11 IndicateBattery:u8(0..100) + Charging:u8 + ChargingMode:u8。
0x21 → 0xA1FF11 GATT Read，可选。Read 返回业务帧；也接收 FF11 Indicate文件数摘要：FileCount:u16LE。不是文件同步的必要条件。
0x22 → 0xA2FF12 Write，Offset:u16LE + PageSize:u8。FF12 Indicate文件分页列表。每条固定 FileName[17] + FileLength:u32LE；没有回显请求 Offset。
0x23 → 0x23FF13 Write，文件名槽位，断点时附 Offset 和 ChunkSize。FF13 Notify 连续数据帧下载。每帧是 FileOffset:u32LE + DataLength:u16LE + FileData；DataLength=0 代表结束。

7. 功能如何使用，以及 App 和设备各自做什么

设备发现

H-EVT-01
怎么使用

进入“设备”页，点击“查找附近设备”。等待设备出现在列表，按 RSSI 选择目标设备。没有找到时，检查设备是否在广播、手机蓝牙是否开启、权限是否允许。

App 接口处理

调用系统 BLE Scan，不写任何 GATT 命令。当前兼容扫描会显示所有有名称设备；同一设备实时更新，不显示无名称设备。用户手动连接后才执行严格 GATT 合约校验，不能通过校验的设备不会进入认证页。

固件必须做到

正常用户态持续广播正确的 AIPIN_XXXX、A3 89 + 6B 地址 和 AF30。名称、地址、服务 UUID 可分布在广播包和 Scan Response，但必须能在短时间内都被手机看到。

成功和失败

成功：列表出现一条带名称和 RSSI 的设备。
失败：错误广播不会显示；设备关机/停止广播 5 秒后会从列表消失。这是预期的实时列表行为。

连接、服务发现和 CCC 准入

H-EVT-02
怎么使用

在已选设备下点击“连接设备”。页面会先显示连接中，成功后进入设备详情并显示“设备认证（EVT）”。此时还没有完成认证。

App 接口处理

停止扫描，连接设备，发现 GATT 服务，校验 9 个必需端点的完整 UUID 和属性，然后按本页第 4 节固定顺序开通 CCC。连接和服务发现各 15 秒，单个订阅准备最多 8 秒。

固件必须做到

FA10、FB10、FF10 服务及必需特征必须在服务发现时出现，且属性与表格完全一致。业务 Indicate/Notify 不能先于对应 CCC 被打开时发送。

成功和失败

成功：9 个必需 CCC ready 后才进入“认证通道就绪”。
失败：缺特征、属性不对、CCC 开启失败或订阅流关闭，App 立即断开，不会向固件继续发送认证/控制命令。

认证、首次绑定和恢复初始认证码

H-EVT-03
怎么使用

连接完成后，在“设备认证（EVT）”卡片中：已有认证码选“认证设备”；首次设置设备认证码选“首次绑定设备”；已认证后可选“恢复初始认证码”。恢复操作有二次确认，因为固件端会清理录音和配置。

App 接口处理

向 FA19 写入 0x09，Content 固定 7 字节：Action:u8 + SecurityCode[6]。Action 0 是认证、1 是绑定、2 是恢复。只接受 FA19 Indicate 的 0x89，Content 恰好为 01 才成功。

固件必须做到

必须从 FA19 接收 Write，并从同一 FA19 Indicate 回 0x89。V1 语义与 V2 不同：01 成功、00 失败。EVT 不发送 Ticket、Nonce、Proof、动态 Scope 或 V2 Action。

成功和失败

成功：App 进入本连接的已认证态，授予状态、配置、文件三类操作权限 60 秒。
失败：认证等待 2 秒且不自动重发；超时、写失败、错误长度或未知结果后直接断开并要求重新连接，避免迟到的 0x89 被错配。

认证后的自动同步和手动刷新

H-EVT-04
怎么使用

认证成功后，App 自动加载设备详情。页面中的“刷新设备状态”可再次读取当前状态；用户不需要手动下发初始配置。

App 接口处理

依次请求 ATT MTU（目标 517，准入最低 136）、FA11 0x01、FA12 0x02，再读取 FA16 状态、FB11 电量、FA15 存储、FA12 UTC、FA16 隐私时长和可选 FF11 文件数。

固件必须做到

0x81 的字段长度须符合协议且 ProtocolVersion=3；设备应支持足够 MTU 承载最大信息帧。0x82 的 01 只能在 12 字节配置和 RTC 都已实际生效后返回。

成功和失败

成功：App 才切到可操作设备详情。
失败：0x01、协议版本或基线 0x02 出错会断开；详情中的补充读取失败只显示“暂未读取”并记日志，不伪造数据。

设备状态、录音授权和默认隐私时长

H-EVT-05
怎么使用

在设备详情查看隐私状态、剩余时间和同步状态；通过“允许设备录音”开关决定是否授予设备录音；点“默认隐私时长”选择设备默认时长。

App 接口处理

所有操作都走 FA16 0x06。读状态用 SubCmd 01；设置录音授权用 02；读/设置默认隐私时长用 03/04。写成功后，App 会再次读取对应值验证，不能只相信一次写响应。

固件必须做到

从 FA16 Indicate 返回 0x86，请求响应中 SubCmd 必须与请求一致、Result 必须为 00、DataLength 必须准确。设备状态变化时可主动发 SubCmd 80，App 会直接刷新显示。

成功和失败

成功：页面显示回读后的真实状态。
失败：SubCmd、长度、Result 或枚举值不合法，App 不更新 UI，并提示操作失败。0x02 不负责这类隐私/授权设置。

设备录音控制

H-EVT-06
怎么使用

设备详情中的“设备录音”区域可执行开始、暂停、继续和结束；按钮会根据最后一次设备状态切换。正在执行时按钮禁用，避免重复点击。

App 接口处理

向 FA17 写 0x07，Content 只包含一个 Action：1开始、2暂停、3恢复、0结束。App 只在从 FA17 Indicate 收到并验证 0x87 后更新状态。

固件必须做到

停止状态的 0x87 Content 只能是 1 字节 RecordStatus=0；录音、暂停、恢复状态必须是 8 字节，包含录音时长、当前时长、模式、类型和降噪字段。Action 和最终状态必须一致。

成功和失败

成功：收到真实 0x87 后，页面显示正在录音/暂停/待机。
失败：0x07 是非幂等动作，超时不自动重发，避免“开始”被重复执行或“暂停”变成恢复；用户应刷新状态或重新连接确认设备实际状态。

电量、存储空间和文件数量

H-EVT-07
怎么使用

在设备详情点击刷新即可更新电量、充电、存储和文件数。文件数仅用于摘要，实际以“设备录音文件”列表为准。

App 接口处理

存储使用 FA15 GATT Read 得 0x85；电量使用 FB11 GATT Read 得 0x91；文件数使用可选 FF11 GATT Read 得 0xA1。三项都已提前订阅，用于接收设备主动变化。

固件必须做到

GATT Read 的返回数据仍是完整 0xED 业务帧。存储字段是总量和剩余量的 u32LE，剩余不能大于总量；电池是 0..100；文件数是 u16LE。

成功和失败

成功：读取或主动 Indicate 都能刷新页面。
失败：Read 2 秒超时可重读一次；第二次仍失败或数据非法时保留旧值，显示未读取/失败，不影响已认证会话。

设备录音文件列表、下载和导入

H-EVT-08
怎么使用

在“设备录音”区域点击“设备录音文件”。App 会自动分页加载设备文件；对某一条点击下载图标“保存到 App”。成功后可以从“查看已保存录音”进入本地记录。

列表接口处理

App 向 FF12 写 0x22，Content 是 Offset:u16LE + PageSize:u8。默认请求 10 条，实际按 min(请求值, 20, floor((MTU-10)/21)) 收敛，要求 ATT MTU ≥ 31。设备从 FF12 Indicate 回 0xA2。

下载接口处理

首次下载向 FF13 写 0x23 + FileName[17]；续传追加 StartOffset:u32LE + ChunkSize:u16LE。当前 ChunkSize 始终为 0，由固件按 MTU 决定块大小。设备从 FF13 Notify 连续回传 Offset、长度、数据。

固件必须做到

0xA2 的每条是固定 21 字节：FileName[17]（最多 16 个可打印 ASCII，NUL 后全零）+ FileLength:u32LE。0x23 的每一块 offset 必须连续，最后必须发送 DataLength=0 结束帧。

App 的严格校验

文件名槽位作为不透明键完整保存并回传；不只使用显示文本。下载每块必须与预期 offset 和长度一致，累计字节必须等于 0x22 声明文件长度，只有终止帧和长度都正确才导入 App。

失败和边界

文件列表：0xA2 不回显 Offset，所以超时、异常或取消后 App 会断开连接，避免迟到列表混进下一页。
下载：15 秒没有下一帧、用户取消、offset 跳变、长度错误或无结束帧都会失败并断开；已收连续数据的 checkpoint 保留，下次可续传。

当前文件边界：EVT 不调用 0x26，不做文件元数据、CRC-32、归档确认或设备侧删除。设备文件下载到 App 后，设备端原文件保留。当前支持导入 .m4a 与 .ogg；iOS 可保存 Ogg/Opus，但未内置 Ogg/Opus 解码器，不能承诺原生直接播放。

断开、自动回连和前后台

H-EVT-09
怎么使用

用户点击“断开设备”会弹出确认，确认后主动断开；意外断开时详情页给出“重新连接”。App 已有成功连接记录时，在前台会自动寻找最近一次已认证设备。

App 接口处理

认证成功并进入可操作状态后，本地保存平台 connectionId、厂商数据解析出的物理地址、显示名和最近成功时间。回连时扫描严格广播，优先用物理地址匹配；连接成功后仍完整走服务发现、CCC、认证和同步，绝不复用旧会话权限。

重试策略

意外断连后在前台最多尝试 3 次：先尝试一次，失败后等待 1 秒，再失败等待 2 秒，之后给用户“重新连接”入口。手动断开会抑制本次前台自动回连，直到用户主动重新连接。

前后台

App 进入后台时停止扫描和自动回连，避免在后台持续扫描；回到前台可恢复流程。断开、认证窗口过期或传输出现歧义时，取消所有订阅和临时流，再重新建会话。

实时日志和联调定位

H-EVT-10
怎么使用

设备详情右上角点“实时日志”，查看本次操作的扫描、连接、订阅、读写、回包、断连与回连时间线。Debug 包可从日志页导出当前日志路径给固件同事比对。

App 记录什么

会记录扫描结果的脱敏摘要、连接状态、服务发现数量、CCC 开始/确认/失败、MTU、写入长度、回包 CMD/长度、解析失败、传输异常和回连次数。认证码、完整协议正文、完整设备 ID 和音频正文不会写入日志。

文件位置

内部日志：应用 Support 目录的 logs/aipin-YYYY-MM-DD.log。Android Debug 镜像：Download/AIPIN/logs/aipin-YYYY-MM-DD.log。iOS Debug 镜像：Documents/AIPIN/logs/aipin-YYYY-MM-DD.log。

保留规则

单文件最多 5 MiB，保留最近 7 个文件；日志页面内存中最多显示 500 条。日志写入/镜像失败不会影响 BLE 功能本身。

8. 超时、重试、断连和错误处理

场景当前 App 策略为什么这样做固件联调检查点
BLE 连接未建立连接等待最多 15 秒；失败或立即断开后进入失败状态。避免页面长期卡在连接中。检查广播、系统配对、连接参数、设备是否只允许单连接。
服务发现失败服务发现等待最多 15 秒；失败就断开。没有可靠 GATT 视图不能继续发协议。检查服务是否在连接后立即可用，UUID 是否为完整 V1.5 UUID。
必需端点或 CCC 不可用任何必需端点属性不匹配、CCC 8 秒未 ready、流错误或流关闭，均中断并断开。防止设备能收到 Write 但 App 收不到业务结果。检查特征属性、CCCD 权限、Indicate/Notify 类型和开启 CCC 后的设备行为。
0x01、0x02、0x06 无响应业务命令响应等待 2 秒，最多重发 1 次。这些操作是可安全重复的读/配置类操作。检查首次/重试帧是否都收到，回包是否在正确特征和 2 秒窗口内。
0x09 无响应等待 2 秒，不重发，断开当前会话。V1 回包没有事务 ID；绑定/恢复可能已改变设备状态，重放危险。检查 FA19 是否在 CCC ready 后回 0x89，以及 Result 是否为单字节。
0x07 无响应不重发；页面提示失败，用户刷新或重新连接确认实际状态。录音动作非幂等，重复发送可能造成状态反转。检查 FA17 的 0x87 状态、长度和真正执行时机。
GATT Read 超时FA12、FA15、FB11、FF11 的 Read 每次 2 秒，允许再读一次。读取是幂等的，允许一次恢复性重试。检查 Read Response 是否携带完整业务帧而不是裸数据。
0x22 文件列表异常不重发；断开当前会话后要求重连。0xA2 不包含请求 Offset，迟到包无法与下一页安全关联。检查每页 0xA2 是否及时发送且 Count/长度准确。
0x23 下载停顿/取消连续 15 秒没有文件帧，或用户取消/帧不连续时，保留 checkpoint 并断开。防止旧 Notify 在下一次下载时混入。检查 Notify 连续性、Offset、Length、结束帧和停止传输的时机。
CRC、长度、CMD 或端点不匹配丢弃无效数据，保留旧状态，写入诊断日志。任何格式错误都不能变成 UI 成功。抓 HCI 日志核对原始字节、Length、CRC 和特征 UUID。
手动断开取消订阅、关闭临时传输、撤销认证权限，抑制本次前台自动回连。尊重用户主动断开。设备侧应正确释放连接资源，允许后续重新连接。

9. Android 和 iOS 平台适配

项目AndroidiOS联调注意点
扫描权限Android 12+ 需要蓝牙扫描/连接权限；低版本通常还需要定位权限和系统定位服务。由 CoreBluetooth 授权；用户可在系统设置中修改授权。App 无权限不会扫描。联调前先确认系统授权状态。
打开蓝牙蓝牙关闭时 App 可请求系统显示开启确认。iOS 不允许 App 直接打开系统蓝牙，只能提示用户到系统设置或控制中心开启。两端文案不同是系统限制，不是协议差异。
扫描数据广告包与 Scan Response 可能拆分成多次回调，App 有 5 秒合并窗口。系统通常以 CoreBluetooth 扫描回调提供可见字段，平台 ID 不是物理 MAC。固件应把三类身份字段稳定广播，不能依赖单一平台的偶然行为。
CCC原生插件按特征属性开 CCC；Indicate 特征不要同时宣告 Notify。CoreBluetooth 用 setNotifyValue(true)，系统按特征属性处理 Notify/Indicate。App 在两个平台统一等待原生订阅 ready，不要在固件侧假设“写成功即已订阅”。
MTUApp 请求 517，读取实际协商值；V3 基础信息要求实际 ATT MTU ≥ 136。系统的 MTU 表达由插件做转换，App 同样以 ATT MTU 判断。固件必须能配合至少 136；文件列表要求至少 31。
设备音频播放导入的设备音频由现有播放器尝试播放。能保存，但系统 AVPlayer 不原生播放 Ogg/Opus。不要把 iOS 的 Ogg 播放列为已完成 EVT 能力。
后台App 进入后台停止扫描和自动回连。同样不保持后台扫描/回连。需要后台长期连接是后续产品能力，当前 EVT 不承诺。

10. 联调验收顺序和 Checklist

固件先自检

  • 广播同时具备正确名称、8 字节厂商数据和 AF30 服务 UUID。
  • 9 个必需特征 UUID 与属性完整；FF11 可选但若存在应为 Read + Indicate。
  • Indicate 特征不同时声明 Notify；FF13 只声明 Write + Notify。
  • 每个 Read/Indicate/Notify 返回完整 0xED 帧，CRC、Length、小端序正确。
  • 认证成功才允许受保护命令；协议版本固定返回 3。
  • 文件列表页、文件数据 Offset、结束帧和声明文件长度一致。

App 与固件逐项验证

  • Android 和 iOS 各扫描 10 次，广播字段完整时稳定显示，关机后 5 秒内消失。
  • 连接后核对 9 个必需 CCC 的顺序、类型和原生 ready 日志。
  • 用正确/错误 V1 安全码验证认证、首次绑定和恢复初始码的 0x09 → 0x89。
  • 验证 MTU、0x01 → 0x81、0x02 → 0x82 和 ProtocolVersion=3。
  • 验证状态、授权、隐私时长、电量、存储、录音控制、文件列表和下载。
  • 验证主动断开、意外断开自动回连、蓝牙关闭、权限拒绝、文件传输中断与日志导出。

推荐日志对照顺序

App: scan_result
 -> connect_start / connection_state=connected
 -> service_discovery_success
 -> notification_subscribed
 -> notification_subscription_confirmed
 -> session_authentication_ready
 -> FA19: 0x09 / 0x89
 -> att_mtu_ready
 -> FA11: 0x01 / 0x81
 -> FA12: 0x02 / 0x82
 -> authentication_synchronization_started
 -> FA16 / FB11 / FA15 / FF11 刷新
 -> FA17 录音 或 FF12/FF13 文件操作

定位问题时应同时保留 App 日志、固件日志和必要时的 Android Bluetooth HCI 日志。先确认“App 有没有发到正确特征”，再确认“固件有没有在正确特征且 CCC 已开启后回包”，最后再查字段内容；不要只凭页面提示判断协议链路。
