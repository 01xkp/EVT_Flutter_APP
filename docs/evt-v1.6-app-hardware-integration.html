AIPIN App 与 V1.6 EVT 固件联调说明

这份文档用于让 App、固件和测试人员对齐同一件事：当前 EVT 构建到底会发什么、设备应当在哪里回什么、页面何时认为操作成功，以及问题出现时如何按日志定位。它只覆盖当前 App 已实现的设备 BLE 链路，不把未开放功能写成已支持。

1. 文档范围

当前 App 的 EVT 白名单只有十个设备命令：0x01、0x02、0x05、0x06、0x07、0x09、0x11、0x21、0x22、0x23。App 只会把这些命令发送到设备，也只会订阅这些命令对应的响应特征。

App 已实现

扫描、连接、GATT 校验、CCC 订阅、V1 六字节认证、状态与配置、设备录音控制、文件列表和断点下载、前台回连、Debug 联调日志。

固件必须配合

正确广播身份，提供指定服务、特征、属性和 CCCD；从正确特征回传正确业务帧；严格使用规定的 Indicate 或 Notify 类型。

本次明确不做

FA18/0x08 实时音频、FF16/0x26 元数据与归档、OTA/WQOTA、0x09 V2 Ticket/Proof、云端票据和云端归档、Factory/UART。

判断成功的标准：GATT Write 成功只表示手机系统蓝牙栈已接收写入请求，并不表示固件已执行。App 必须收到对应特征的业务回包，校验帧格式、CRC、CMD 和字段后，才会更新页面为成功状态。

2. App 和设备怎么协作

01用户界面查找、连接、认证、设置、录音、导入文件。
02会话控制器判断已连接、已认证、权限、当前设备状态和按钮可用性。
03协议层组装业务帧、校验发送数据、等待匹配响应、解析字段。
04BLE 传输层扫描、GATT 连接、服务发现、Read、Write、MTU、订阅。
05系统蓝牙栈Android Bluetooth GATT 或 iOS CoreBluetooth 配置 CCC 并传递数据。
06设备固件接收 Write、执行实际动作、从规定特征 Indicate 或 Notify 回包。
用户点击“开始录音”
  -> App 检查：当前设备已连接、认证未过期、FA17 已订阅、设备已允许录音
  -> App 向 FA17 写入：0x07 请求帧
  -> 固件开始录音
  -> 固件从 FA17 Indicate 返回：0x87 + 最新录音状态
  -> App 校验 CRC、CMD、特征和状态字段
  -> 页面才显示“正在录音”

控制类回包使用 Indicate，链路确认由系统蓝牙栈完成，App 不会额外发送一条业务 ACK。FF13 文件数据使用 Notify，由协议中的 Offset、长度和结束帧保证顺序和完整性。

3. 扫描和识别设备

用户在设备页点击“查找附近设备”后，App 申请系统权限并开始 BLE 扫描。当前 EVT 调试版遵循此前的联调要求：不做严格广播过滤，只显示“有名称”的蓝牙设备；没有名称的设备不显示。这样可以方便发现广播字段仍在调整中的 EVT 样机。

App 目前如何更新列表

同一设备只保留一条记录。后续广播会刷新 RSSI、名称、厂商数据、服务 UUID 和最后发现时间；5 秒没有再次收到广播则移出列表。因此已关机、离开范围或停止广播的设备不会继续停留在页面。

为什么连接后还要校验 GATT

扫描不严格过滤意味着列表里可能有其他 BLE 设备。用户点击连接后，App 会发现服务并验证 V1.6 EVT 的九个必需特征和属性。GATT 不符合时会结束会话，不能进入认证、录音或文件操作。

固件应发送的正式广播身份

广播字段固件 V1.6 EVT 应提供当前 App 行为联调意义
Local NameAIPIN_XXXX，其中 XXXX 是地址最后两个原始字节的大写十六进制。扫描阶段只要求名称非空；名称格式暂不作为准入条件。正式产品稳定识别设备，也便于人工确认样机。

连接 ID 不是同一种东西：Android 的连接 ID 通常是 MAC 地址；iOS 由 CoreBluetooth 返回 UUID，不能当作物理 MAC。App 回连时优先使用厂商数据中的 6B 地址，缺失时才退回平台连接 ID。

订阅顺序为什么分两阶段

认证前

App 只订阅 FA11 和 FA19 的 Indicate。FA11 用于取得脱敏身份，FA19 用于认证结果。此时 App 不读取受保护状态，不会向业务特征发送控制命令。

认证后

App 依次订阅 FA12、FA15、FA16、FA17、FB11、FF12、FF13，设备有 FF11 时最后订阅。每个订阅都会等待原生 CCC 配置完成及 Dart 监听器就绪。

App 不会在 CCC 还未完成时抢先发送能立即回包的命令。每个必需订阅最长等待 8 秒，CCC 确认后额外等待一个很短的监听器稳定窗口，避免设备快速 Indicate 落在原生到 Dart 的切换间隙。

5. 从连接到可操作的完整流程

用户选择有名称的 BLE 设备
  -> 停止扫描，建立 GATT 连接
  -> 发现服务与特征，校验 9 个必需 EVT 特征和属性
  -> 订阅 FA11、FA19 的 Indicate CCC
  -> 协商至少 ATT_MTU=99
  -> FA11 写 0x01，读取未认证 0x81 脱敏身份
  -> 用户输入 6B 安全码，FA19 写 0x09
  -> FA19 Indicate 返回 0x89 成功
  -> 订阅其余业务特征，FF11 有则额外订阅
  -> 协商目标 ATT_MTU=517；认证态完整信息最低要求 136
  -> FA11 写 0x01，读取认证态 0x81，并记录 ProtocolVersion
  -> FA12 写 0x02 下发当前 UTC 与 EVT 基线录音参数（AudioStream 固定为 0）
  -> 自动读取状态、电量、存储、默认隐私时长、可选文件数量
  -> 设备页面进入可操作状态

ProtocolVersion：当前 V1.6 约定值是 3。App 会记录设备回传的版本值到日志，但按当前联调约定暂不因版本不等于 3 而阻止连接，方便发现仍在调整中的样机。正式量产前应恢复版本准入校验。

认证、首次绑定和恢复初始认证码

用户动作发给 FA19 的 0x09 Content固件应做什么App 成功条件成功后的下一步
认证设备Action=0x00 + SecurityCode[6]校验当前连接的六字节安全码。FA19 Indicate 0x89，Content 只有 1B 且值为 0x01。开启业务订阅、同步信息与配置。
首次绑定设备Action=0x01 + SecurityCode[6]按固件定义要求用户实体确认，并写入新的安全码。先收到 0x89 = 0x01。App 在同一 GATT 连接自动再发一次 Action=0x00；第二次认证成功后才开放业务。
恢复初始认证码Action=0x02 + SecurityCode[6]按 V1.6 清除或恢复语义完成设备侧操作后再回包。收到 0x89 = 0x01。App 清除本地回连记录和文件下载断点，并主动断开。

当前 EVT 页面输入 12 位十六进制字符，每两位转换为一个原始字节，共 6B。它不发送 Ticket、Proof、Nonce 或 V2 认证载荷。V1.6 所描述的 HTTPS 取码服务尚未接入当前 EVT 页，现场需提供正确的六字节安全码。

6. App 怎么发送、怎么接收、怎么判定成功

这一节是现场对包时最重要的部分。它说明一次“点击按钮”在 App 内部如何变成 BLE 字节包，又如何从手机收到的字节恢复成页面上的结果。除了 0x11 和读取设备 UTC 的 FA12 Read 外，所有业务请求均遵循“向指定特征 Write With Response，等待指定特征的 Indicate/Notify 业务帧”的方式。

6.1 一次业务 Write 的完整发送过程

01用户或自动同步触发控制器先检查连接、认证、权限、当前录音状态和功能范围。
02构建 Content仓库按接口字段写入 u8、u16LE、u32LE 或固定 ASCII 槽位。
03本地参数校验检查命令白名单、固定长度、枚举、文件名和 EVT 的 AudioStream=0。
04组装完整业务帧添加 ED、Length、小端 CRC16；Debug 日志记录完整 raw_packet_hex。
05先注册等待器在实际 GATT Write 前设置 expected CMD/SubCmd，避免快速回包先到而丢失。
06Write With Response原生 BLE 层向指定特征写入；写完成后才开始计算业务回包超时。

这里有两个“成功”，不要混淆：evt_command_transmit_completed 表示手机的 ATT Write 已完成；它之后 App 仍在等固件业务响应。只有收到并校验对应 0x8x 或 0xAx 帧后，才会记录 evt_command_completed 并更新页面。

6.2 App 实际发出的通用帧

[0xED][Length_L][Length_H][CMD][Content...][CRC_L][CRC_H]

Length  = CMD(1B) + Content(NB) + CRC16(2B)
CRC16   = 对 [CMD + Content] 计算 CRC-16/CCITT-FALSE
u16/u32 = 小端序：低字节在前，高字节在后

示例：认证码为 01 02 03 04 05 06，执行“认证设备”
Content = 00 01 02 03 04 05 06
发送帧 = ED 0A 00 09 00 01 02 03 04 05 06 CRC_L CRC_H
            |  |  |  |  \-----------------/
            |  |  |  |        0x09 的 7B Content
            |  |  |  CMD = 0x09
            |  |  Length = 10 = 1 + 7 + 2
            |  帧头后的长度为 Little Endian

上例中的 CRC 两个字节不是固定值，App 每次都会根据 CMD 和 Content 实时计算。联调时不要手工套用上次日志的 CRC，必须用本次真正发送的字段重算。

长度对照：未认证 0x81 只能是 90B Content，且 ReservedFeatureStatus、录音状态、存储和最后 6B 状态都应为 0；认证态在没有 30B 保留区时，停止/错误为 90B、录音/暂停为 97B，有保留区时分别为 120B、127B。App 对长度和这些条件字段都严格校验。

6.6 一次回包在 App 内部如何被接收

  1. Android/iOS 原生 BLE SDK 收到 Indicate 或 Notify，转交给对应特征的 Dart 订阅流；GATT Read 的值则直接返回给 Read 调用。
  2. App 为每个特征分别维护组帧器。一个协议帧被拆成多次 BLE 回调时会缓存等待；一次回调包含多个帧时会依次拆开，绝不会把不同特征的数据拼在一起。
  3. 组帧器确认同步字 0xED、Length、完整帧长度后，编码器检查 CRC-16/CCITT-FALSE。失败帧记录原始字节和原因后丢弃。
  4. 成功解析后，命令客户端先确认是否有正在等待的请求，再匹配期望响应 CMD；0x06 还必须匹配 SubCmd；0x07 还要匹配目标录音状态。
  5. 匹配成功才解除该命令的等待。随后协议仓库再校验业务 Content 的固定长度、枚举、Offset 或文件大小，并把最终模型交给页面。
  6. 未匹配的有效帧不直接丢弃：会以主动事件形式记录，例如设备主动 0x86 状态变化；但它不能错误地完成另一个用户操作。

FF13 的差异：文件下载不是“每个数据包都发一个请求”。App 仅 Write 一次 0x23，固件随后连续 Notify 0xA3，直到发送零长度结束帧。App 在此期间独占命令队列，避免其它请求和文件流交叉。

7. 协议帧和接口清单

6.1 通用业务帧

[0xED][Length:u16LE][CMD:u8][Content...][CRC16:u16LE]

Length = CMD(1B) + Content + CRC16(2B)
CRC = 对 CMD + Content 计算 CRC-16/CCITT-FALSE
多字节字段 = 小端序（Little Endian）

App 会按每个特征独立缓存数据，支持一个 BLE Value 被拆成多次回调，或多个协议帧粘在同一次回调中。同步字、长度或 CRC 不正确的帧会丢弃并写日志，不会误更新页面状态。

命令写入或读取位置预期响应用于什么当前 App 处理重点
0x01FA11 WriteFA11 Indicate 0x81设备信息、设备码、软件版本、协议版本、录音状态。预认证只接受脱敏布局；认证后读取完整布局并记录 ProtocolVersion。
0x02FA12 Write；设备时间为 FA12 GATT ReadFA12 Indicate 0x82下发当前 UTC 与基础录音参数。固定 12B 配置，录音模式为 EVT 固定值，AudioStream=0。
0x05FA15 Write，Content 为空FA15 Indicate 0x85查询总存储和剩余存储。这是业务 Write + Indicate，不把 FA15 当作 GATT Read。
0x06FA16 WriteFA16 Indicate 0x86读取状态、设置录音授权、读取/设置默认隐私时长。必须同时匹配 CMD 与 SubCmd；主动状态事件也会更新页面。
0x07FA17 WriteFA17 Indicate 0x87开始、暂停、继续、结束设备录音。只有收到真实状态才更新 UI；不自动重试，避免重复执行。
0x09FA19 WriteFA19 Indicate 0x89V1 认证、绑定、恢复初始码。Content 固定 7B：Action + 6B 原始码；不自动重试。
0x11FB11 GATT ReadRead 值中的 0x91读取电量、充电状态、充电模式。它不是业务 Write，App 不会把 0x11 塞入写命令队列。
0x21可选 FF11 Write，Content 为空FF11 Indicate 0xA1兼容性文件数量摘要。FF11 不存在或订阅失败不影响其它 EVT 功能。
0x22FF12 WriteFF12 Indicate 0xA2分页读取文件名和文件长度。从 Offset=0 开始，直到 Count=0；请求不自动重试。
0x23FF13 WriteFF13 Notify 连续 0xA3下载一个设备录音文件。独占命令队列，按 Offset 连续写入，0 长度数据帧表示结束。

6.2 重点字段说明

0x06 状态与配置

SubCmd=0x01 读取隐私、剩余分钟数、录音授权和同步状态；0x02 设置录音授权；0x03 读取默认隐私时长；0x04 设置默认隐私时长。设置类响应应表明成功且无额外数据；App 会检查请求长度、布尔值和时长编码。

0x07 录音状态

Action 0 结束、1 开始、2 暂停、3 继续。0x87 停止时只有 1B 状态，录音或暂停时是包含时间信息的可变布局；App 严格校验对应长度。

0x22 文件列表

文件项为 FileName[17] + FileLength:u32LE。文件名必须是 ASCII、NUL 结束且后续补零，不能包含路径字符；App 只接受 .m4a 与 .ogg，并要求长度大于 0。

0x23 文件下载

首次请求只带 FileName[17]；续传附加 StartOffset:u32LE + ChunkSize:u16LE，当前 ChunkSize 固定为 0。0xA3 每帧带 FileOffset:u32LE + DataLength:u16LE + FileData；DataLength=0 是结束帧。

8. 用户可用功能和每个功能的真实流程

查找设备

H-EVT-01

怎么使用

进入设备页，点“查找附近设备”。设备应在蓝牙范围内并持续广播。列表中选择目标设备后再点连接。

App 做什么

检查蓝牙和运行时权限，开始扫描，合并同一设备的广告包与 Scan Response，实时更新 RSSI。当前显示所有有名称的设备。

固件要做什么

持续发送 BLE 广播。建议稳定包含 AIPIN_XXXX、A3 89 + 6B 和 AF30，确保回连和后续正式过滤稳定。

失败时看什么

先看 App 日志中的权限、蓝牙状态、扫描启动和 scan_result_received。没有结果时再用系统蓝牙工具确认设备是否实际广播。

连接、服务发现和订阅

H-EVT-02

怎么使用

在设备列表点击目标设备。不要在页面仍显示“正在连接”时立即开始认证，等页面进入“设备认证（EVT）”。

App 做什么

停止扫描，建立连接，发现服务，校验特征属性，打开认证前 CCC，读取脱敏身份。任何必需端点不符合就显示连接失败而不是伪造已连接。

固件要做什么

服务发现后立即暴露完整 GATT；FA11/FA19 要有 Indicate + CCCD，并在手机启用 CCC 后可靠回传业务响应。

关键判断

成功：日志先出现 CCC 已配置和监听器 ready，再出现未认证 0x01 → 0x81。
失败：Write 能成功但 CCC 未 ready，后续响应必然收不到，App 会在连接阶段停止。

认证、首次绑定、恢复初始认证码

H-EVT-03

怎么使用

点击“认证设备”或“首次绑定设备”，输入 12 位十六进制码。恢复初始认证码是破坏性操作，确认后才发送。

App 做什么

把 12 个字符解成 6B，向 FA19 写 0x09，先挂起等待回包再执行 GATT Write。这样即使固件回包早于 Write 完成通知，App 也不会丢失 0x89。

固件要做什么

从 FA19 接收 Write，并从同一特征 Indicate 1B 结果：0x01 成功、0x00 失败。首次绑定应遵循 V1.6 的实体确认要求，完成后再返回成功。

特别说明

绑定成功后 App 会立即发同一连接的认证请求，不会因为“绑定成功”直接开放业务。恢复成功后 App 清除本地设备记录并断开。

认证后自动同步与手动刷新

H-EVT-04

怎么使用

认证成功后页面会自动加载。用户也可点击刷新，重新获取设备状态、电量、存储和时间。

App 做什么

建立所有业务订阅，协商 MTU，读取认证态 0x81，再写 0x02 基础配置，并读取状态、电量、存储和默认隐私时长。

固件要做什么

支持认证后完整信息布局，接受基线配置并回 0x82；对状态类读取回对应特征的正确业务帧或 Read 数据。

页面显示规则

设备信息和配置必须来自最近一次校验成功的响应。补充读取失败时 App 保留旧值或显示“暂未读取”，不会编造数据。

录音授权、隐私时长和同步状态

H-EVT-05

怎么使用

在设备详情调整“允许设备录音”或默认隐私时长，并可刷新状态查看剩余隐私时间和同步状态。

App 做什么

所有操作都走 FA16 的 0x06 → 0x86。读取、设置、主动上报按 SubCmd 区分，设置成功后再刷新本地设备状态。

固件要做什么

正确解析 SubCmd 和数据长度；设置成功时回 Result=成功的对应响应。状态主动变化时可用规定的 0x86 事件布局上报。

失败时

App 会保留上次有效状态、提示请求失败，并记录 CMD、SubCmd、特征和回包等待结果。不会把“写入已提交”误显示为“设备已设置”。

设备录音控制

H-EVT-06

怎么使用

认证后，待机时点击开始；录音中可暂停或结束；暂停后可继续或结束。实际按钮由最近一次设备录音状态决定。

App 做什么

向 FA17 写 0x07，等待 FA17 Indicate 0x87。该命令不会自动重发，因为重复的暂停、继续或结束可能改变设备真实状态。

固件要做什么

执行动作后回最新状态；停止使用 1B 状态布局，录音和暂停按 V1.6 定义使用可变长度布局。固件不要只回 Write ACK 而不回 0x87。

失败后怎么处理

等待超时后页面不强行切状态。用户可以刷新设备信息或断开重连确认实际录音状态，日志可用于区分“未收到命令”和“未收到回包”。

电量、存储和文件数量

H-EVT-07

怎么使用

认证后的设备详情自动展示，也可手动刷新。文件数量只在固件提供 FF11 时展示。

App 做什么

FB11 用原生 GATT Read 获取电量；FA15 写空 Content 的 0x05 获取存储；FF11 存在时写空 Content 的 0x21 获取兼容文件数量。

固件要做什么

FB11 Read 返回规定 0x91 数据；FA15/FF11 从 Indicate 回正确 0x85/0xA1，不能将它们作为裸 GATT 值回传。

兼容策略

FF11 缺失或错误时只隐藏文件数量摘要。文件列表和导入仍走必需的 FF12/FF13，不会被 FF11 阻断。

设备文件列表、下载和导入

H-EVT-08

怎么使用

打开设备录音文件页。文件列表加载后，选择一个 .m4a 或 .ogg 文件并点击导入。断开后重新导入同一文件可继续。

App 做什么

先用 FF12 的 0x22 分页获取文件清单；导入时只向 FF13 写一次 0x23，随后持续接收 0xA3 Notify，按 Offset 连续写入私有临时文件。

固件要做什么

0x22 按请求 Offset 回 0xA2；0x23 后从 FF13 Notify 连续推送数据。每帧长度必须匹配实际 FileData，最后必须发送 DataLength=0 的结束帧。

当前范围边界

最终收到的字节数必须等于文件列表声明长度。成功后 App 保存到本地记录，但不会发送 0x26、CRC-32 确认、归档确认或删除指令，设备上的原文件会保留。

断开和自动回连

H-EVT-09

怎么使用

用户主动点断开后，App 不会自动回连。意外断连后，只要 App 在前台且设备仍在广播，App 会尝试找到最近一次认证成功的设备。

App 做什么

保存显示名、平台连接 ID 和可用的物理地址。意外断连后重新扫描，优先按物理地址匹配，最多尝试三次，间隔约 1 秒、2 秒。新连接仍需重新发现、重新认证和同步。

固件要做什么

保持广播身份稳定，允许新连接后的完整 GATT 流程。固件不应假定前一连接的 CCC、认证或未完成文件下载在新连接中继续有效。

后台边界

App 进入后台会停止主动扫描和回连，回前台后恢复。iOS 声明了 central 模式，但系统仍可能因策略暂停进程；不能把后台持续连接当作 EVT 验收的必然结果。

实时日志与联调定位

H-EVT-10

怎么使用

设备详情页右上角进入“实时日志”。现场出现问题时导出同一时段的 App 日志，并与固件串口日志、必要时 Android HCI 日志按时间比对。

App 记录什么

扫描、连接、服务发现、特征属性、CCC 配置、MTU、发送帧、Write 完成、回包等待、原始响应、超时、断开、回连和文件传输 Offset。

日志文件在哪里

内部路径为应用 Support 目录下的 logs/aipin-YYYY-MM-DD.log。Android Debug 会尝试镜像到 Download/AIPIN/logs；iOS Debug 可通过 Documents 文件共享导出。

联调安全提醒

当前 Debug 的 raw_packet_hex 会保留完整收发字节，可能包含认证码、文件名和音频字节，只能用于受控联调。Release/Profile 不持久化这类完整原始包。

9. 超时、重试和异常处理

场景当前 App 行为为什么这样处理固件侧优先排查项
连接或服务发现超时连接会话阶段失败并断开，不进入认证页面。没有可靠 GATT 视图不能安全发送协议。广播是否稳定、是否只允许单连接、服务是否及时暴露。
必需特征或属性不符合显示 GATT 不完整并结束会话。避免出现“写成功但永远收不到正确回包”的假连接。特征 UUID、Read/Write/Indicate/Notify 属性和 CCCD 是否齐全。
CCC 未 ready / 流关闭最长等 8 秒；必需订阅失败则中断会话。没有可靠回包监听时，不允许操作设备。CCCD 写入结果、Indicate/Notify 模式是否与特征匹配。
普通单次命令无响应等待约 2 秒，读取和幂等配置类最多重试 1 次。给偶发 BLE 丢包一次恢复机会，又限制重复执行。首次和重试 Write 是否收到，响应是否从正确特征在超时前发出。
0x07 或 0x09 无响应不自动重试，提示失败或要求重新认证。录音控制、绑定、恢复码不是幂等动作，重发可能造成重复状态改变。FA17/FA19 是否在 CCC ready 后回 0x87/0x89，字段长度是否正确。
0x22 文件列表异常不自动重试当前页，结束本次会话后要求重新连接。迟到的 0xA2 不含请求 Offset，下一页无法安全区分。Count、每项长度、文件名槽位、响应时机。
0x23 文件流停止15 秒未收到下一帧即超时，保留连续 Offset 的 checkpoint。防止旧数据流混入下一次下载，支持后续断点续传。FF13 Notify 是否连续；Offset、DataLength、结束帧是否正确。
CRC、长度、CMD、SubCmd 或端点不匹配丢弃无效帧，保留旧 UI 状态，并写入完整诊断日志。任何格式异常都不能变成页面成功。对照原始十六进制、Length 小端序、CRC 算法、回包特征 UUID。
系统配对或加密不足提示用户在系统蓝牙中完成配对后再试。App 不调用私有 API 强制配对，保持 Android/iOS 兼容。设备是否要求加密、配对流程是否已在系统层完成。

所有命令在开始等待回包前都会生成一个 wait_id。日志会依次记录 evt_response_wait_started、evt_response_wait_armed、等待中的 evt_response_waiting，以及完成、超时、中断或取消的终态。写入尚未完成前不开始计算业务回包超时；提前到达的回包也能被命令等待器匹配。

10. Android 与 iOS 平台适配

平台场景当前 App 处理联调时应确认
Android 6 - 11 扫描按系统版本请求位置权限，并检查系统定位服务状态。授权后能扫描到 Legacy 广播和 Scan Response；拒绝权限时页面给出明确提示。
Android 12 及以上请求 BLUETOOTH_SCAN 和 BLUETOOTH_CONNECT 附近设备权限。Manifest 保留 neverForLocation，与不申请定位权限的运行时策略保持一致；否则底层扫描库还会要求精确定位权限并返回未授权。首次授权、关闭蓝牙、重新打开蓝牙、已配对/未配对设备都能走正确提示和连接流程；使用真机确认主广播和 Scan Response 可被接收。
Android 连接 ID通常可见 MAC，但 App 不假定所有设备或 Android 版本都永久稳定；回连优先使用广播物理地址。同一设备重启或 App 重启后，回连仍能匹配到相同硬件。
iOS 蓝牙权限Info.plist 声明蓝牙使用说明，使用 CoreBluetooth 授权和扫描。首次授权、拒绝授权、系统蓝牙关闭与再次开启后，用户可重新扫描。
iOS 打开蓝牙App 不能直接开启系统蓝牙；只能引导用户在系统设置或控制中心开启后返回 App。不要把 iOS 的系统限制误认为固件或 App BLE 写入失败。
iOS 文件播放设备文件可下载和保存；iOS 原生播放器不保证 Ogg/Opus 可播放。若固件输出 OGG，应将“下载成功”和“可播放”分开验收；M4A 是当前跨平台更稳妥格式。
前后台iOS 声明 bluetooth-central，但系统资源调度仍可能暂停 App；Android/iOS 都不承诺后台持续主动扫描。本次 EVT 重点验证前台意外断连回连；后台长期连接需单独列为后续专项。

11. 日志怎么读，怎么和固件日志对照

推荐对照顺序

  1. App 是否扫描到目标广播。
  2. 是否真正完成连接和服务发现。
  3. 目标特征是否存在，属性和 CCC 模式是否正确。
  4. App 是否记录 CCC ready，才发送命令。
  5. App 写入的特征 UUID、CMD、原始十六进制包是什么。
  6. 固件是否收到同一包，并从同一规定特征发回响应。
  7. App 是否收到原始回包；若收到，CRC/CMD/长度为何被接受或丢弃。

一条认证日志应形成的时间线

FA19 CCC configured
-> notification_subscription_ready
-> security_code_sheet_confirmed
-> legacy_authentication_requested
-> evt_response_wait_started
-> evt_command_transmit_completed
-> notification_received (FA19)
-> evt_response_wait_finished
-> legacy_authentication_succeeded

如果停在 transmit_completed，说明 App 已把 Write 提交给系统蓝牙栈，下一步只能等待设备从已订阅的 FA19 Indicate 返回 0x89；需要对照固件是否实际 Indicate 以及手机是否收到回调。

日志不等于固件执行成功：请按“App 发包 → 固件收到 → 固件入队/执行 → 固件回包 → App 收包 → App 协议校验成功”六步判断。任何一步缺失都能缩小问题范围，不能只看页面 Toast 或单侧日志下结论。

12. EVT 真机联调验收清单

固件先自检

  • 广播包含稳定名称、A3 89 + 6B 和 AF30。
  • 九个必需特征存在，服务 UUID、特征 UUID 和属性与本文第 4 节一致。
  • 控制特征只提供 Indicate；FF13 只提供 Notify，不要把 CCC 类型做反。
  • 每个 CCC 可写入且开启后真实生效。
  • 帧 Length、CRC-16/CCITT-FALSE、小端序、CMD 和字段长度完全符合 V1.6。
  • Action=1 的实体确认、Action=2 的清除完成后才返回成功。

App 与固件逐项验证

  • Android 和 iOS 都能扫描、显示、连接并通过 GATT 校验。
  • 先只有 FA11/FA19 CCC，再验证预认证 0x01 → 0x81。
  • 正确/错误安全码分别验证 0x09 → 0x89；首次绑定额外确认自动 Action=0。
  • 认证后所有业务 CCC、MTU、认证态 0x01 → 0x81、0x02 → 0x82 正常完成。
  • 逐项验证 0x06、0x07、0x05、0x11、可选 0x21。
  • 验证 0x22 至少一页列表、0x23 完整导入和一次断连续传。
  • 验证主动断开不回连、意外断开前台回连、权限拒绝、蓝牙关闭和日志导出。

交付判断：当上述项目均能在真实设备上以 App 日志、固件日志和必要抓包共同证明时，才可以称为“V1.6 EVT 联调通过”。当前代码和自动化测试已覆盖 App 侧协议、订阅、拆包粘包、超时和平台配置，但不能替代真实固件的 GATT 属性、CCC 和实际回包验证。
