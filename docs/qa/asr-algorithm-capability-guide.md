# 开源语音转写、对齐、说话人、检索与总结算法库能力整理

> 本文只讨论可复用的开源模型、运行库和通用算法策略，以及它们的许可证核查方法；不涉及具体产品、终端、接口或实施方案。Star 数是 2026-09-14 的 GitHub 检索快照，只用来衡量社区热度，不代表准确率或实时性。

## 先看结论

一套完整的“录音变文字再变总结”通常不是一个模型，而是下面这条流水线：

```text
声音
 -> 切成连续音频帧
 -> VAD 判断有没有人在说话
 -> ASR 把声音变成文字
 -> 标点、数字、专有名词规范化
 -> 时间戳和说话人
 -> 从原文挑出关键段落
 -> 对长文本分块总结并合并
 -> 输出摘要、决定、待办、风险和问题
```

最重要的三句话：

1. **实时转写的关键是“连续输入 + 模型记忆”，不是简单切文件。**
2. **关键段落必须保留原文和时间范围，不能只让模型凭空改写。**
3. **长录音要先分块总结，再合并和查冲突；一次把全文塞给模型通常不稳。**

例子：模型听到“下周一把报价单发给客户”时，实时阶段可能先显示“下周把报价单…”。等后面听清“周一”和“客户”，才把这一句盖章为最终文字。关键段落模块会保留这句话的原文和时间点；总结模块再把它整理成“待办：周一发送报价单，负责人未提及”。

## 1. 先把几个词说清楚

### 1.1 音频帧不是文件分片

“音频帧”是按时间切出来、可以连续播放的声音片段，例如 20 毫秒的 PCM 数据。“文件分片”只是把文件的字节从中间截开。

```text
正确：PCM 时间 0~40 ms、40~80 ms、80~120 ms，按顺序输入模型
错误：把一个 M4A 文件从第 5 MB 截到第 6 MB，当成一条新录音
```

普通 M4A 的索引或元数据（例如 `moov`）可能在文件尾部；即使它在文件开头，任意字节片段也不保证能独立解码。算法需要的是连续的可解码音频和时间顺序，而不是任意字节块。

常见术语可以这样记：

| 术语 | 解释 |
| --- | --- |
| sample（采样点） | 每秒记录很多个振幅数字；16 kHz 就是每秒 16,000 个数字 |
| frame（音频帧） | 连续的一小段时间窗口，常见是 10~30 ms 左右 |
| chunk（推理块） | 一次送进模型的多帧音频，通常比单帧大 |
| 文件/网络分片 | 按字节传输的一段数据，不代表一段完整的时间音频 |
| segment（句段） | 模型认为相对完整的一句或一小段文字 |
| token | 模型处理的字或字词碎片，不一定等于一个汉字 |
| cache（模型记忆） | 模型为下一块保留的上下文状态，不是完整文字 |

### 1.2 离线、准实时、真流式

| 名称 | 解释 | 常见特点 |
| --- | --- | --- |
| 离线 | 全部录完后再识别 | 上下文最完整，通常准确率较高，等待时间长 |
| 准实时 | 录音过程中反复对最近窗口重算 | 能较快显示，但会重复计算和修改文字 |
| 真流式 | 主要输入新增声音，同时沿用模型规定的有限回看、右上下文和状态 | 延迟和成本更稳定，需要专用 streaming 模型或策略 |

Whisper 原始推理入口更接近离线/准实时；Paraformer streaming、Vosk、部分 sherpa-onnx 模型和 Moonshine 从设计上更接近真流式。

### 1.3 partial 和 final

- `partial`：草稿，后面听到更多声音后可能会改。
- `final`：本次流式会话里暂时确认的句段，通常不再改；录音结束后全量重跑仍可能得到更好的版本。

如果把每次 partial 都直接追加，屏幕会出现：

```text
第一次：我们准备
第二次：我们准备下周
第三次：我们准备下周一发报价单

错误结果：我们准备我们准备下周我们准备下周一发报价单
```

正确做法是把同一个句段当成一个可更新的对象，直到它变成 final。

### 1.4 一张表看懂每个模块的边界

| 模块 | 它主要解决什么 | 它不能保证什么 |
| --- | --- | --- |
| VAD（语音活动检测） | 找出哪一段有人讲话、何时停顿 | 不识字、不认人、不负责标点 |
| ASR（自动语音识别） | 把声音变成文字 | 不保证文字一定是事实 |
| 标点/数字规范化 | 把无标点文字整理得更好读 | 可能改错数字，不能替代原始文字 |
| 时间对齐 | 给句、词或字标上音频时间 | 不能修正识别错的内容 |
| 说话人分离 | 区分匿名的甲、乙、丙 | 不自动知道真实姓名，抢话时也可能错 |
| 关键段落抽取 | 从原文挑出值得定位的证据 | 不应凭空改写成新事实 |
| 摘要 | 把较长文字压缩成结论 | 可能漏信息或幻觉，必须回指原文 |

### 2.2 Whisper：质量高，但实时要额外做工作

**项目类型**：通用多语言 ASR 基座模型和参考实现。官方仓库同时提供模型、Python 推理代码、命令行工具和论文，适合做质量基线。

**核心算法**：输入音频先变成 log-Mel 频谱，Transformer encoder 提取声学上下文，decoder 再按 token 一个一个生成文字。训练时用特殊 token 表示转写、翻译、语言识别等任务，因此同一套模型可以完成多种语音任务。长音频通常按约 30 秒上下文窗口滑动处理；窗口长度是典型实现约束，不应当理解成所有衍生模型都完全相同。

**能力清单**：

- 多语言语音转文字；多语言模型还可以把非英语语音翻译成英语。
- 语言识别、跨语言转写和较强的噪声/口音泛化能力。
- 返回句段级时间范围；token 时间可作为估计值，词/字级精确时间通常要另做强制对齐。
- 输出通常自带一定标点，但没有独立可调的标点、说话人分离和结构化文本模块。
- 训练任务里有 VAD 相关 token，但这不等于一个可单独替换、可精确调端点的 VAD 组件。

**实时性和资源**：原始 `transcribe()` 会读取文件并以滑窗方式重复计算，属于离线或准实时基座，不是原生连续流式模型。要边听边显示，需要重叠窗口、增量解码、去重和稳定前缀策略；窗口越多，重复计算越明显。模型从 tiny/base 到 large/turbo 有明显的速度、显存和准确率取舍，不能只看模型名称判断体验。

**功能完整度**：识别能力完整，但不包含字幕版本管理、说话人、关键段落和总结流程，需要在外层组合。

**商用核查**：官方仓库声明代码和官方模型权重采用 MIT；从 Hugging Face 或其他镜像取得的转换权重、量化文件和附加组件仍应固定来源与版本，逐项查看对应 Model Card。MIT 只解决许可，不解决识别质量、隐私和运维问题。

**适用判断**：多语言录后转写、质量基线、后续用 faster-whisper/WhisperX 精修时优先考虑。对严格低延迟字幕、低功耗端侧和需要原生词级时间戳的场景，不宜直接把原始 Whisper 当成完整方案。

**例子**：一句话从第 29 秒说到第 31 秒。第一窗口只听到“我们明天”，第二窗口只听到“开会”。没有重叠会截断语义，重叠太多又会重复“我们明天”；因此实时封装必须同时处理上下文和去重。

### 2.3 faster-whisper：让 Whisper 跑得更快

**项目类型**：Whisper 的推理实现，不是另一套训练出来的 ASR 模型。它用 CTranslate2 执行 Whisper，并支持 CPU/GPU、FP16/INT8、批处理和多种模型格式。

**核心能力**：

- 继承 Whisper 的多语言转写、翻译和分段能力，主要改变执行速度和内存占用。
- 支持 batch 推理、beam size、温度回退等常见解码参数，适合一次处理很多文件。
- 可输出词级时间戳（由 Whisper token 时间估计），并可启用 Silero VAD 过滤静音；这两个能力不是同一个算法。
- 可以加载官方 Whisper 或转换后的兼容权重；自定义微调权重也可以先转换再运行。

**实时性和资源**：它本身主要面向文件/分段推理，不自动提供模型级状态 cache 或稳定的 partial/final 输出。把短片段不断送入 faster-whisper 可以做准实时，但要自行处理重叠、重复和稳定前缀。GPU 批处理通常吞吐高，CPU/INT8 可降低成本；实际 RTF 受模型大小、beam size、语言和并发影响。

**功能完整度**：作为“高吞吐 ASR 引擎”较完整；仍缺 VAD 状态机、说话人分离、强制对齐、关键段落和总结，需要叠加其他模块。WhisperX 常把它作为 ASR 推理引擎，再叠加对齐和说话人模块。

**商用核查**：faster-whisper 和 CTranslate2 代码为 MIT，但使用的 Whisper 权重、第三方 VAD 权重和自定义转换文件要按各自来源核查。转换脚本能改变文件格式，不会改变原权重的许可条件。

**适用判断**：录音结束后的高吞吐重跑、批量文件和 GPU 环境精修是强项。若目标是原生低延迟流式，需另配 streaming 模型或增量调度层。

**不要混淆**：

```text
faster-whisper = 更快地运行 Whisper
实时算法      = 连续输入、状态缓存、稳定输出
```

前者不能自动替代后者。它特别适合录音结束后的高质量重跑。

### 2.4 FunASR：完整的语音工具箱

**项目类型**：面向工业语音识别的工具箱和模型集合，覆盖 offline、streaming 和 edge。FunASR 不是一个固定模型，而是把 ASR、VAD、标点、说话人、情绪/音频事件和部署入口组织在同一套生态里。

**能力清单**：

- ASR 模型：Paraformer、SenseVoice、Fun-ASR-Nano 以及多语言/领域模型。
- VAD：FSMN-VAD、Silero VAD 等，负责起声、停声和切段。
- 文本后处理：CT-Punc 标点、数字/文本规范化、热词和时间段输出。
- 说话人：CAM++ 等 speaker embedding 与聚类，输出录音内匿名 speaker index。
- 额外任务：情绪识别、笑声/掌声等音频事件、语音增强和多种运行时/服务方式。

**实时性和资源**：是否真流式由所选 checkpoint 决定。`Paraformer-zh-streaming` 有 chunk、cache、look-back 和 `is_final` 规则；`SenseVoiceSmall` 的常见用法是分段推理，不能因为都由 FunASR 加载就假定共享同一 streaming 状态。CPU、GPU、量化和边缘运行时各有不同的速度/内存取舍。

**功能完整度**：在中文“VAD + ASR + 标点 + 匿名说话人 + 情绪/事件”链路中，组件覆盖最广，适合快速做完整能力验证。缺点是模型、运行时和参数较多，组件组合不当会造成时间戳、speaker 和版本不一致；关键段落与长文本总结仍需另做。

**商用核查**：FunASR 软件代码为 MIT，但官方 `MODEL_LICENSE` 对模型权重及衍生模型另设协议，要求署名、保留模型名并附免责声明，且协议可修订；SenseVoice/Paraformer 的具体 checkpoint 还要看各自 Model Card。不能用 MIT 代码许可证替代权重审查。

**适用判断**：中文实时、录后整理、端侧和 GPU 环境都值得把 FunASR 作为第一批候选；若只需要单一 ASR 推理或希望最少依赖，应比较直接使用 sherpa-onnx、faster-whisper 或 WeNet 的成本。

**例子**：同一套流水线可以先用 FSMN-VAD 找出语音，再用 Paraformer 出中文文字、CT-Punc 补标点、CAM++ 分匿名说话人；换成 SenseVoice 后还可多出情绪/事件标签，但每个模块的时间轴和许可证仍需分别核对。

### 2.5 Paraformer streaming：中文实时的重点候选

**项目类型**：Paraformer 是 ASR 模型路线，FunASR 是包含模型、VAD、标点、说话人和部署工具的工具箱。不能把“FunASR”简单等同于某一个模型；同一个工具箱里的离线 Paraformer、streaming Paraformer 和 SenseVoice 的能力不同。

**核心算法**：Paraformer 属于非自回归路线，预测器先估计输出长度和声学/语义表示，再并行生成一批 token，减少逐 token 解码的等待。streaming checkpoint 把连续音频组织成 chunk，并保存 encoder/attention cache 和规定的 look-back，使后一块能够利用前一块的上下文。

**能力清单**：

- `paraformer-zh` 等离线模型：中文普通话转写、句段时间和较高吞吐。
- `paraformer-zh-streaming`：连续输入、低延迟 partial、句末 `is_final`/flush；chunk、look-back 和 cache 必须按该 checkpoint 的规则。
- FunASR 工具链还可组合 FSMN-VAD、CT-Punc 标点、CAM++ 说话人 embedding、情绪和音频事件模型。
- 可按模型选择 CPU、GPU、ONNX/其他推理运行时；部署形态不代表每个模型都支持相同任务。

**实时性和资源**：官方示例常见约 600 ms 的 chunk（例如 `chunk_size=[0,10,5]`），这是某个模型/采样率的起点，不是通用标准。chunk 越小，首字更快但上下文和吞吐可能变差；look-back 太短会丢跨块语义，太长会增加延迟和计算。

**功能完整度**：在中文实时链路上较完整，能把 ASR、VAD、标点和说话人组件组合起来；但“组合完整”不等于“一个模型全包”。关键段落、长文本总结和实名声纹仍需外层算法。

**商用核查**：FunASR 代码仓库为 MIT，但每个 checkpoint 都有自己的 Model Card/模型许可；部分 FunASR、SenseVoice 权重使用单独的模型协议，可能包含署名、模型名、用途和免责声明要求。商用前要锁定模型 revision、权重来源和第三方组件，不能只看工具箱代码许可证。

**适用判断**：中文实时字幕、实时草稿和服务器部署环境的低延迟识别应优先做基准测试。跨语言、极端噪声或需要统一词级对齐时，应与 Whisper/Qwen3-ASR 等路线在同一测试集比较。

**例子（为便于理解省略了模型规定的有限回看/右上下文）**：

```text
第 1 块：听到“今天我们”       cache = C1
第 2 块：只输入新增“讨论方案”  使用 C1，得到 cache = C2
第 3 块：只输入新增“改版”      使用 C2，得到 cache = C3
```

如果每次都从录音开头重新识别，就失去了 streaming 的主要优势。每条独立音频流要有独立 cache，结束时用模型规定的 `is_final=true` 或 flush 方式提交尾部；句段结束后 cache 是清空、滚动还是保留，也要按模型实现处理。

### 2.6 Vosk：小而直接的在线识别

**项目类型**：基于 Kaldi/WFST 传统在线解码路线的离线 ASR API。模型、词典和语言模型一起工作，强调小模型、低内存和持续接收音频。

**能力清单**：

- 支持多种语言和平台，音频到达一段就可以返回中间结果，断网也能运行。
- 可返回句段/词级时间和解码置信度；置信度是模型分数，不等于事实正确率。
- 可用 grammar/词表限制候选，例如只识别“开始、暂停、下一页”，对固定指令很有效。
- 某些模型或扩展支持说话人向量、关键词和标点，但这些不是所有 Vosk 模型的默认能力。

**实时性和资源**：Vosk 的 `AcceptWaveform` 风格接口天然适合逐帧输入，延迟主要由帧大小和 endpoint 参数决定。模型通常比大型 Transformer 小，CPU 运行成本低；代价是开放域长句、远场噪声、口音和多人重叠的准确率上限通常较低。

**功能完整度**：在线听写和固定词表指令较完整；长语音标点、全局说话人分离、词级精确对齐、关键段落和总结需要额外组件。它是轻量识别器，不是完整长语音理解系统。

**商用核查**：Vosk API 代码通常采用 Apache-2.0，但官方和社区模型的许可并不统一，可能出现 GPL/AGPL/LGPL 或非商业条款。必须核对实际下载的语言模型和词表，不能只看 API 仓库许可证。

**适用判断**：离线指令、嵌入式和资源受限环境值得优先评估；中文开放域长语音应与 Paraformer、Whisper 等在同一噪声集上实测，不要凭“小模型”或“原生流式”推断准确率。

**例子**：把 grammar 限定为“开始录音、暂停录音、结束录音”时，Vosk 可以快速给出稳定指令；同一模型拿来识别多人讨论的专业名词，可能因词典和语言模型覆盖不足而频繁错字。

### 2.7 SenseVoice：不只输出文字

**项目类型**：多任务语音模型。SenseVoice 的重点不是只把字识出来，还把语言、情绪和非语言音频事件作为额外输出；常见的 SenseVoiceSmall checkpoint 覆盖中文、英语、粤语、日语和韩语，其他版本的语言范围要看模型卡。

**核心算法**：它采用非自回归的声学建模思路，在一次分段推理中同时预测文字和任务标签。这样可以减少逐 token 生成的等待，适合短段低延迟处理；标签头和 ASR 文字是不同任务，不能用情绪标签替代转写置信度。

**能力清单**：

- 多语言语音转写和语言识别。
- 情绪类别、笑声/掌声/咳嗽等音频事件标签（具体标签集取决于 checkpoint）。
- 与 FSMN-VAD、CT-Punc、CAM++ 等组件组合，形成带断句、标点和匿名说话人索引的流水线。
- 可在 CPU/GPU 上运行；也有量化或其他运行时转换，但转换后要重新验证准确率和标签输出。

**实时性和资源**：SenseVoice 本体常见用法是分段/短音频推理，低延迟不等于所有版本都提供原生连续流式状态。严格流式需要确认具体 checkpoint 是否有 streaming cache，或由外层按音频块封装；硬切块会影响情绪和事件判断的上下文。

**功能完整度**：在“文字 + 语言 + 情绪/事件”这类多任务识别上较完整；说话人分离、实名识别、精确词级对齐、关键段落和长文本总结仍是独立模块。情绪和事件是概率标签，不是对人的医学或人格判断。

**商用核查**：SenseVoice 代码仓库为 MIT，但 SenseVoiceSmall 等权重通常沿用 FunASR 的模型协议，具体署名、用途和再分发条件必须按 Model Card/固定 revision 审核。第三方 VAD、说话人和对齐模型另算许可证。

**适用判断**：需要多语言、情绪或音频事件提示时值得评估；只需要中文最低延迟字幕时，Paraformer streaming 往往更直接。涉及高风险情绪判断时必须保留人工复核和原音证据。

**例子**：同一句“好的”，文字可能一样，但音频事件和情绪标签可以帮助区分普通回应、笑着回应或叹气。标签只能作为辅助信号，不能据此断定说话人的真实意图。

### 2.8 whisper.cpp：把 Whisper 放进本地运行时

**项目类型**：Whisper 的 C/C++ 推理实现和 `ggml` 运行时，不是新的声学模型。它提供命令行、C API、多平台绑定、CPU/GPU/NPU 后端和量化模型格式。

**能力清单**：

- 在 Windows、Linux、macOS、Android、iOS、WebAssembly 等环境运行 Whisper。
- 支持 CPU-only、Metal、Core ML、CUDA、Vulkan、OpenVINO 等后端（具体能力随构建版本和硬件变化）。
- 支持整数量化，降低模型磁盘和内存占用；量化级别越激进，速度/内存收益和识别损失需要实测。
- 仓库有连续采样、VAD 和语音助手示例，可作为端侧实时原型。

**实时性和资源**：连续采样示例通常用滑窗重复推理，不能因为“有实时示例”就当成带稳定 partial/final 的原生 streaming checkpoint。上下文窗口、线程、量化和硬件加速决定 RTF；同一模型在桌面 CPU、移动 CPU 和 NPU 上差异很大。

**功能完整度**：本地推理能力完整，长音频理解能力不完整。没有内置生产级说话人分离、词级强制对齐、关键段落或总结；这些要由上层组合。

**商用核查**：whisper.cpp 代码采用 MIT；模型文件、转换脚本产生的权重和后端依赖仍要按来源核对。量化或改名不改变原权重的许可义务。

**适用判断**：需要本地、离线、低依赖和跨平台时优先评估。若追求中文长句准确率，应在目标终端上比较量化等级与 Paraformer/sherpa-onnx 模型，不能只看桌面演示速度。

**例子**：同一个 `base` 模型，桌面 GPU 可以实时以上运行，低端 CPU 可能只能慢速处理；把模型量化到更小尺寸可以降低内存，但“姓氏/型号”这类词可能先受到影响。

### 2.9 sherpa-onnx：跨平台模型运行时和能力集合

**项目类型**：ONNX/C++ 运行时和模型封装，不是单一 ASR 算法。它可以承载 Zipformer/Transducer、Paraformer、CTC、Whisper、Moonshine 等不同模型，也提供 VAD、关键词唤醒、TTS、说话人和音频处理接口。

**能力清单**：

- online streaming 和 offline ASR；可在同一运行时切换模型和平台。
- Android、iOS、Windows、Linux、macOS、WebAssembly、嵌入式等多种构建目标。
- 多种 VAD、关键词、说话人识别/分离、标点和 TTS 组件，适合做本地完整语音工具链。
- 支持模型量化、线程配置和硬件后端；实际延迟、内存和算子兼容性取决于具体模型。

**实时性和资源**：只有选用 online checkpoint 时才有模型级状态和低延迟；把 offline Whisper 或任意 ONNX 文件放进运行时，不会自动获得真流式。chunk、look-ahead、cache 和 endpoint 均随模型而定。

**功能完整度**：作为部署层很完整，作为“质量保证”并不自带答案。模型 zoo 中的语言、训练数据、时间戳和许可证各不相同，必须把运行时与实际 checkpoint 一起评估。

**商用核查**：runtime 通常是 Apache-2.0；模型 zoo 可能包含 Apache、CC-BY、GPL/非商业或其他条款。商用发布要记录每个模型包的来源、revision、SHA-256 和许可证，不能用 runtime 许可证覆盖权重。

**适用判断**：需要跨平台本地推理、统一 C/C++ 接口或一套运行时承载多种模型时很实用。若只做单一云端 ASR，使用它的收益可能不如直接采用模型官方后端。

**例子**：同一套 sherpa-onnx 代码可以加载中文 Paraformer streaming，也可以加载英文 Moonshine；代码接口相似，但两者的词表、延迟、时间戳和商用条款完全可能不同。

### 2.10 Moonshine：面向实时的小模型路线

**项目类型**：从模型结构和运行库设计上面向 live streaming 的轻量 ASR。它与 whisper.cpp 的关系不同：whisper.cpp 是 Whisper 的实现，Moonshine 是另一套模型/运行时路线。

**能力清单**：

- 以较小模型和短上下文实现连续语音识别，适合 CPU、浏览器或低功耗场景。
- 运行库提供流式输入、增量结果和多平台集成方向；具体语言、时间戳和后端能力按模型版本查看。
- 可作为端侧实时模型与 Paraformer、Vosk、sherpa-onnx 的对照组。

**实时性和资源**：模型小、首字延迟和内存通常有优势，但小模型的词汇、口音、远场噪声和长上下文上限不能直接与 Whisper large 比较。流式状态仍需正确管理，短 chunk 不会自动解决断句和重复。

**功能完整度**：实时 ASR 核心较聚焦；标点、说话人、词级对齐、关键段落和总结需要外层组件。普通话/非英语支持不能从英文模型的表现推断。

**商用核查**：默认 streaming/English 模型通常采用 MIT；旧的非英语或普通话 legacy 模型可能适用 Moonshine Community License，包含 non-commercial 或收入门槛。必须按实际模型文件和版本核对，不要只看仓库代码许可证。

**适用判断**：低功耗端侧、实时指令和快速原型值得测；中文长语音、跨语言和高准确率录后场景应把它作为候选而非默认答案。

**例子**：同一运行环境中，Moonshine 可以较快识别“下一页”这类短指令；遇到多人同时讨论、长句和中文专名时，应与更大模型做 CER 和稳定延迟对照。

### 2.11 WhisperX：把“听懂”变成“可精确回放”

**项目类型**：基于 Whisper 的录后处理流水线，不是新的端到端声学模型。典型链路是 VAD 分段 -> faster-whisper 批量转写 -> wav2vec2 等语言匹配模型做 forced alignment -> pyannote 做说话人分离。

**能力清单**：

- 把句段或 token 时间进一步对齐到词/字，适合搜索、字幕和按词定位音频。
- 批处理和 VAD batching 可显著提高长录音吞吐；官方 README 的速度数字依赖 GPU、batch size、模型和语言，不能照搬成固定保证。
- 可给每个词绑定匿名 speaker label，并把 speaker label 传播到句段。
- 支持多语言，但 forced-alignment 模型是语言相关的；没有合适的音素模型时，只能保留粗粒度时间。

**实时性和资源**：设计目标是录后批处理，不是连续低延迟字幕。对齐阶段要再次读取音频和完整文字，GPU 内存、模型下载和处理时间都高于单次 ASR；重叠说话、数字、符号和词典外专名可能无法对齐。

**功能完整度**：在“转写 + 词级时间 + 匿名说话人”上较完整，但不负责流式会话、关键段落、长文本总结或实名声纹。WhisperX 的 VAD、ASR、alignment、diarization 是可替换组件，换组件后质量和许可证也随之变化。

**商用核查**：WhisperX 代码为 BSD-2-Clause；默认 pyannote speaker-diarization-community-1 需要接受模型条款和访问权限，常见许可为 CC-BY-4.0。wav2vec2、Whisper/faster-whisper 和其他模型各自核查，不能只看 WhisperX 的代码许可证。

**适用判断**：录后精修、词级时间定位和说话人标注优先评估；严格实时字幕应先用 streaming ASR，结束后再把 WhisperX 结果作为第二遍定稿。

**例子**：普通 ASR 只给“00:10~00:18 我们下周一发报价单给客户”；对齐后可以得到“我们(10.2~10.5s)、下周一(11.0~12.0s)、发(12.1~12.3s)”，但若“2014”不在对齐词典里，该词可能没有词级时间。

### 2.12 pyannote.audio：说话人分离和声纹特征

**项目类型**：音频分段、说话人分离（diarization）和 speaker embedding 工具/模型生态，不是 ASR。WhisperX 常用它给已识别的句段贴匿名说话人标签。

**核心算法**：先检测语音活动，再把连续语音切成小段；模型为每段提取 speaker embedding（声音特征向量），最后按相似度聚类并做时间边界修正。输出的是 `SPEAKER_00`、`SPEAKER_01` 等匿名簇，不是自动识别姓名。

**能力清单**：

- 说话人分离：回答“什么时候是谁在说话”。
- speaker embedding：可用于同一录音内聚类，也可在有授权的前提下做注册声纹匹配。
- 支持离线全局聚类；部分 pipeline 可做近实时，但在线聚类可能发生 speaker split/merge，录后重聚类通常更稳。
- 可与 ASR 句段、词级时间和重叠语音检测组合，生成带说话人的转写。

**实时性和资源**：全局聚类需要看到更多录音，低延迟模式的标签可能回改。`speaker-diarization-community-1` 主要按完整音频离线运行；pyannote.audio 另有可逐块运行的 VAD/分段组件，但把它们拼成在线聚类后仍可能发生 speaker split/merge。多人抢话、短句、相似音色和单通道混音是主要难点；真正分开重叠语音还需要语音分离或多麦克风。

**功能完整度**：说话人能力强，但不识字、不补标点、不做总结，也不能单凭 embedding 证明真实身份。要显示“张三”，还要有已授权的声纹注册库和身份映射。

**商用核查**：`pyannote.audio` 代码仓库采用 MIT；`speaker-diarization-community-1` 模型卡是 gated，需接受 Hugging Face 使用条件并使用访问令牌，模型许可标注为 CC-BY-4.0。代码、模型卡、模型依赖和任何已注册声纹数据的授权要分别留档，具体归因要求以模型页为准。

**适用判断**：长语音需要按人归属、质检和时间定位时值得组合使用；若只需要单人转写，加入它会增加算力和误分风险。

**例子**：两人轮流说话时可输出“00:00~00:05 A、00:05~00:08 B”；若两人同时说“对”，单通道 pipeline 可能只保留一个人或把字串在一起。

### 2.13 WeNet：中文生产流式和 two-pass 路线

**项目类型**：面向训练、导出和部署的端到端 ASR 工具箱，核心是 U2/U2++ 等统一的流式/非流式架构，不是单个 checkpoint。

**核心算法**：动态 chunk attention 让 encoder 只看有限左/右上下文，CTC 提供快速单遍结果，attention decoder 或 rescoring 在句末做第二遍重排。这样可以先出低延迟草稿，再用更强的语言约束修正。

**能力清单**：

- 中文普通话等模型的 streaming 和 offline 推理。
- CTC、attention、Transducer、U2/U2++、two-pass 解码和动态 chunk 配置。
- 训练、数据准备、模型导出、ONNX/Runtime 集成和基准工具相对齐全。
- 可接 VAD、标点、热词和自定义语言模型，但不是所有示例都内置这些组件。

**实时性和资源**：chunk 越小延迟越低，但右上下文和语言建模能力变弱；two-pass 会在 endpoint 后增加一次计算。它更适合有 GPU/工程团队做训练和调参的场景，直接拿默认模型并不能保证某种中文口音或远场效果。

**功能完整度**：训练和 ASR 部署能力强，长音频整理仍需外接时间精修、说话人、关键段落和总结。相比只提供推理的库，WeNet 更适合需要改模型或做领域适配的团队。

**商用核查**：WeNet 代码通常是 Apache-2.0；预训练模型、数据集和第三方运行时按各自条款核对。训练数据可用不等于模型权重可以任意再分发。

**适用判断**：中文服务器部署、需要 two-pass 或要自己训练/微调时值得评估；如果只想快速拿一个端侧二进制，sherpa-onnx 或 whisper.cpp 的集成成本通常更低。

**例子**：第一遍 CTC 在停顿前给出“发布日期周五”，第二遍 attention 看到后文“改到下周一”后把句段改正；这就是 two-pass 的速度与准确率折中。

### 2.14 NVIDIA NeMo Speech：训练和 GPU 服务框架

**项目类型**：NVIDIA 的语音训练/推理生态，包含 Conformer、FastConformer、Transducer、CTC、Canary 等模型和数据、训练、导出工具。它是框架和模型集合，不是一个固定 ASR 算法。

**能力清单**：

- 训练、微调、评估和导出 ASR/TTS/语音理解模型。
- 支持 CTC、RNN-T/Transducer、Conformer/FastConformer 等路线，也有流式推理示例和 cache 机制。
- GPU 混合精度、分布式训练、TensorRT/ONNX 等部署路径较丰富。
- 可通过自有数据做热词、领域词和语言适配，适合研究到生产的模型迭代。

**实时性和资源**：能做真流式，但配置、显存、CUDA、模型转换和监控要求较高；“框架支持流式”不代表每个模型或每个导出格式都支持相同延迟。小团队采用预训练模型时要先评估部署复杂度。

**功能完整度**：训练和 GPU 推理能力很全，长音频整理仍要外接 VAD、对齐、说话人和摘要算法。它的价值在可定制和规模化，而不是开箱即用的单一二进制。

**商用核查**：NeMo 代码通常 Apache-2.0；NGC、Hugging Face 或社区模型的权重、数据和依赖可能有不同条款。固定镜像、容器、CUDA 和模型版本，逐项保存许可证。

**适用判断**：有 GPU 集群、需要训练定制或高吞吐服务时适合；只需要一个成熟中文实时模型时，FunASR/WeNet/sherpa-onnx 通常更快进入验证。

### 2.15 Silero VAD：只负责找出“哪里有人说话”

**项目类型**：独立的神经网络 VAD 检测器，不是 ASR。它按短帧输出人声概率，再由状态机形成起声、停声和 endpoint。

**能力清单**：

- 8 kHz/16 kHz 等常见采样率的逐帧语音活动检测。
- CPU 运行、模型小、Python/ONNX 等多种集成方式。
- 可作为 faster-whisper、WhisperX、FunASR 或自定义流式链路的前置门控。
- 通过阈值、最短语音、最短静音、pre-roll 和 hangover 调整误触发与尾部截断。

**实时性和资源**：VAD 很快，但噪声、音乐、键盘声和远场混响会造成误报/漏报。阈值降得太低会把噪声送进 ASR，阈值升得太高会吞掉第一个字；所有时长参数都要用目标环境校准。

**功能完整度**：只解决“何时送入 ASR、何时结束一句”，不识字、不加标点、不区分说话人，也不理解语义。删除静音会破坏原始时间轴，因此 VAD 最好只控制计算，不删除录音。

**商用核查**：代码仓库通常采用 MIT；实际 ONNX/量化权重和被集成的 ASR 模型仍需分别查看来源与条款。

**适用判断**：几乎所有实时或录后语音链路都值得把它作为 VAD 候选，但必须把 VAD F1、首尾截断率和 endpoint 延迟单独测量，不能用 ASR CER 代替。

**例子**：说“我们要——（短暂停顿）开始”时，hangover 可以保持同一句；风扇声连续超过阈值时，VAD 可能误判为有人讲话，这需要噪声校准而不是让摘要模型补救。

### 2.16 WhisperStreaming：用 LocalAgreement 稳定滑窗 Whisper

**项目类型**：流式策略和参考实现，不是新的 Whisper 权重。它把离线 Whisper/faster-whisper 放入滑动窗口，多次解码后只提交稳定文本。

**核心算法**：每次窗口向前移动，得到当前完整假设；将相邻假设按 token/词对齐，取未提交部分的共同前缀（LocalAgreement），连续一致后才锁定。等待更新次数越多，稳定性越好但延迟越高。

**能力清单**：

- 为没有原生 cache 的 Whisper 增加自适应延迟和增量字幕。
- 可切换 faster-whisper 等后端，适合研究不同 chunk、步长和稳定策略。
- 能复用 Whisper 的多语言和翻译能力，但不包含说话人、对齐、关键段落或总结算法。

**实时性和资源**：本质仍会重复处理窗口，长录音的计算量和显存高于原生 streaming 模型；GPU 吞吐会直接影响输出延迟。直接对未对齐字符串求 LCP 会因插入、删除或标点变化误锁字。

**功能完整度**：算法研究价值高，生产功能不完整；VAD、标点、时间对齐、说话人、关键段落和总结需另外组合。

**商用核查**：仓库代码许可和所用 Whisper/faster-whisper 权重、VAD 依赖分别核对；研究代码能运行不等于整套依赖可直接分发。

**适用判断**：想快速验证 Whisper 的实时体验、比较稳定策略时适合；对低延迟和成本有硬指标时，优先测试原生 Paraformer/Transducer。

**例子**：H1“我们准备下周”、H2“我们准备下周一发”、H3“我们准备下周一发报价单”，稳定前缀只能先锁“我们准备下周”，后面的“一发报价单”继续作为草稿。

### 2.17 SimulStreaming：用读写策略控制同步延迟

**项目类型**：面向 simultaneous speech-to-text/translation 的研究型策略，常以 Whisper 作为后端。它关注“什么时候继续听、什么时候开始出字”，而不是重新训练一个 ASR 模型。

**核心算法**：主要策略 AlignAtt 观察 decoder attention 是否已经看到音频末端；若注意力仍集中在末端危险区，就继续读取音频，避免过早输出，满足条件后才写出 token。也可以使用 LocalAgreement 等策略作对照。

**能力清单**：

- 调节质量、首字延迟和回改率之间的平衡。
- 支持实时转写和翻译研究，便于测试不同 policy、窗口和等待规则。
- 可接 Whisper 的多语言能力，但仍受 Whisper 模型大小和 GPU 吞吐约束。

**实时性和资源**：需要 GPU、解码策略和参数调优；attention policy 的延迟表现依语言、语速和模型而变。它是研究型策略，不包含存储或摘要算法。

**功能完整度与商用核查**：策略实现相对聚焦，代码和模型依赖要逐项看许可；商用评估时还要重新测量目标环境的稳定延迟和资源占用。

**适用判断**：研究低延迟同步转写、翻译或比较 policy 时使用；普通中文实时字幕先从专用 streaming ASR 开始更省工程量。

### 2.18 WhisperLive：把 Whisper 组织成近实时服务

**项目类型**：流式推理参考实现，把 Whisper 或 faster-whisper 放进持续音频输入和近实时返回流程。它解决的是“如何组织窗口推理”，不是新的声学算法。

**能力清单**：

- 持续接收音频、批量或增量转写、返回近实时文本。
- 可切换 faster-whisper 等后端，并提供 GPU/CPU 运行示例。
- 适合快速验证窗口、VAD、字幕刷新和服务吞吐。

**实时性和资源**：通常仍属于滑窗/批推理，延迟受窗口、批大小和 GPU 吞吐影响；不应把示例吞吐当成固定指标。说话人、精确对齐、关键段落和总结不是它的核心职责。

**功能完整度**：窗口调度和增量结果示例比直接调用 Whisper 完整，但 VAD、对齐、说话人、关键段落和总结仍需另配。

**商用核查**：仓库代码许可证、Whisper/faster-whisper 权重和推理依赖分开审核；原型能跑不代表所有依赖可闭源再分发。

**适用判断**：用于快速验证窗口策略和性能基线；需要稳定结果时应结合专用 streaming 模型或更严格的前缀稳定算法。

### 2.19 Qwen3-ASR：较新的多语种实时/离线候选

**项目类型**：新一代多语种 ASR 模型和推理代码，提供 offline 与 streaming 路线；能力和限制高度依赖具体模型版本、后端和部署方式。

**能力清单**：

- 覆盖多语言语音转写，具体语言数以 Model Card 为准（当前公开资料列出 52 语言版本）。
- 提供 streaming 推理和离线批处理路径，适合与 Whisper、FunASR 做同音频集对照。
- 可与 Qwen3-ForcedAligner 等后处理组合，补充词/字级时间。

**实时性和资源**：官方 README 当前把 streaming 绑定到 vLLM 后端；streaming 路径不支持 batch，也不直接返回 timestamps。需要词/字级时间时，要在录后用 ForcedAligner（模型卡说明最多约 5 分钟、11 种语言；当前 `qwen-asr` 主分支封装把 `MAX_FORCE_ALIGN_INPUT_SECONDS` 设为 180 秒，实际可用上限随发布版本变化）或其他对齐模型处理。GPU、vLLM 版本和显存是主要门槛。

**功能完整度**：ASR 模型能力较新，服务器 streaming 入口在持续变化；VAD、标点、说话人、关键段落和总结需要另配。时间戳和语言覆盖不能从模型名称推断，必须按版本验收。

**商用核查**：仓库和具体模型以 Apache-2.0/Model Card 声明为准，固定 revision；vLLM、ForcedAligner、量化文件和其他权重另行核对。不要把“开放权重”当成所有衍生文件自动同许可。

**适用判断**：多语言服务器部署的最新候选和对照组；若中文低延迟优先，先与 Paraformer-zh-streaming 在同一数据上比较首字延迟、CER、稳定延迟和词级时间可得性。

### 2.20 Qwen3-ForcedAligner：把已有文字对齐到音频时间

**项目类型**：Qwen3-ASR 配套的非自回归（NAR）强制对齐模型，不是另一个 ASR。输入完整音频、已经确定的文字和语言，输出文字单元的起止时间；它适合录后精修、词级时间定位和把关键段落准确映射回原音频。

**核心算法**：模型卡把它描述为“对任意单元预测时间戳”。当前官方封装的处理过程可以概括为：先把音频统一为单声道 16 kHz，再按语言把中文等 CJK 文本拆成字、空格语言拆成词，日语和韩语使用专用分词；每个文字单元前后放置两个 timestamp 槽位，模型一次前向为这些槽位预测时间桶，最后把成对的时间桶转换成 `start_time`/`end_time`。当前配置的时间桶间隔是 80 ms；封装还会对偶发的非单调时间做单调修正，因此这是模型级时间估计，不应宣传成毫秒级测量。

**能力清单**：

- 支持中文、粤语、英语、德语、西班牙语、法语、意大利语、葡萄牙语、俄语、韩语和日语，共 11 种语言。
- 支持词级或字级输出；实际粒度由语言分词和文本内容决定，标点、符号等字符可能被清洗掉，上层流程要保留原文到对齐单元的映射。
- `qwen-asr` 提供 `Qwen3ForcedAligner.align(audio, text, language)`，可接本地路径、URL、base64 或 `(numpy, sample_rate)`，并支持 batch。
- Qwen3-ASR 的 `return_time_stamps=True` 会调用该对齐器；流式 ASR 本身不返回时间戳，通常在句段 final 或录音结束后再对齐。

**实时性和资源**：这是“给定文字后再对齐”的完整片段推理，不是逐帧 streaming。模型卡写的是单段最多约 5 分钟；当前 `qwen-asr` 主分支代码限制为 180 秒（3 分钟），应锁定包版本并用目标输入实测。更长录音要按已确认句段切块、记录原音频 offset，再合并时间；跨块切句会增加边界误差。0.6B 模型通常需要 GPU/BF16 才能获得合理吞吐，批大小、FlashAttention 和显存会影响成本。

**功能完整度**：词/字级时间能力集中且接口清楚，但它不会纠正 ASR 文字、检测语音、区分说话人、补标点或生成摘要。音频和传入文字不一致时，模型仍会尝试对齐，结果可能出现拖长、压缩或错位；应先保存 ASR 原文和置信度，再把对齐结果当作定位信息。

**商用核查**：`Qwen/Qwen3-ForcedAligner-0.6B` 模型卡和 Qwen3-ASR 代码当前标注 Apache-2.0；`qwen-asr`、PyTorch、Transformers、日语/韩语分词依赖、FlashAttention/vLLM 以及量化文件仍要按实际版本逐项核对。Apache-2.0 解决的是许可条件，不代表时间精度或第三方依赖自动满足实际使用要求。

**适用判断**：需要词级时间定位、文本定位和证据引用时值得优先评估；严格实时场景先用 streaming ASR 输出句段级时间，再调用它补精确时间。若文本经常超过 3~5 分钟、语言不在 11 种范围内或运行环境没有 GPU，应比较 WhisperX、CTC 对齐器或其他端侧方案。

**例子**：ASR final 得到“我们下周一发报价单给客户”。把同一段音频和这句文字传给对齐器后，可得到“我们”“下周一”“发”“报价单”“给”“客户”各自的起止时间；调用方可以按“报价单”的时间定位原始音频。若 ASR 把“报价单”识别成错误词，对齐器只会给错误词找时间，不会替换成正确词。

### 2.21 总结模型和编排工具：负责“写”，不负责“听”

转写结束后，语言模型才把文字整理成摘要。它们与 ASR 是两个层次：

| 类别 | 代表 | 能做什么 | 不负责什么 |
| --- | --- | --- | --- |
| 开放权重指令模型 | [Qwen3](https://github.com/QwenLM/Qwen3)、Qwen2.5-Instruct、Llama 3.x Instruct、Mistral Instruct | 根据已确认文字生成摘要、决定、待办和 JSON | 不直接从波形听出文字；事实必须来自输入证据 |
| 抽取/排序算法 | TextRank、BM25、句向量、MMR | 找中心句、按问题召回、去掉重复 | 不会自动理解缺失的音频，也不等于完整摘要 |
| 编排框架 | LlamaIndex、LangChain | 把分块、并行、合并、重试串起来 | 不会提高 ASR 准确率，也不会自动消除幻觉 |

**模型商用边界**：Qwen3/Qwen2.5 的具体权重通常按 Apache-2.0 Model Card 发布；Llama 3.x 使用 Meta Community License，附带归因、可接受使用和规模条款；Mistral 必须逐 checkpoint 核对，既有 Apache-2.0 模型，也有研究许可模型。框架的 MIT 代码许可证不能覆盖被调用的模型。

**例子**：ASR 输出“预算上限五十万，周五前确认”。总结模型可以整理成“决定：预算上限 50 万，周五前确认”，但不能把“周五”改成“周三”，也不能补一个原文没有的负责人。无论选择哪个模型，都应要求输出来源句段和“未提及/待确认”。

### 2.22 Qwen3：长文本总结和结构化输出模型

**项目类型**：通用指令语言模型，不处理原始音频。Qwen3 提供不同参数规模和 thinking/non-thinking 模式，可承担摘要、分类、抽取和 JSON 生成。

**能力清单**：

- 将已确认的句段整理成摘要、决策、待办、风险、问题和主题。
- 在给定证据 ID 的前提下做结构化输出、字段补全和冲突说明。
- 长上下文和多语言能力适合 Map-Reduce/Tree 摘要，但上下文长度、显存和模式要按 checkpoint 测量。

**实时性和资源**：总结不应跟着每个音频帧调用；可按若干 final 句或数分钟触发增量摘要，结束后再跑全局版本。thinking 模式可能更慢，适合复杂冲突而不是首字字幕。

**功能完整度**：文本总结能力完整，但事实一致性、证据校验、去重和权限控制必须由外层规则实现。模型可以写得很顺，却不能证明原文真的这么说。

**商用核查**：Qwen3 权重和不同量化/转换文件要逐一查看 Model Card 与 Apache-2.0 条款；tokenizer、推理框架和数据集另行核对。

**适用判断**：作为长录音总结和结构化输出候选；先用抽取/检索把证据窗口准备好，再让模型写，可靠性高于直接把整篇原文交给模型自由发挥。

### 2.23 LlamaIndex：分层总结编排

**项目类型**：Python 文档索引和 LLM 编排库，不是 ASR 或摘要模型。

**核心算法**：TreeSummarize 先把文本按上下文窗口重新分块，各块并行生成小结，再递归自底向上合并；Refine 则先用第一块生成答案，随后按顺序带着已有答案逐块修订。

**能力清单**：

- 组织 Map-Reduce、Tree/Hierarchical、Refine、检索增强和结构化输出。
- 管理 token 预算、上下文窗口、并发、重试和不同模型后端。
- 可把句段 ID、时间戳和证据字段一起传入模板，形成可回跳摘要。

**局限和商用核查**：它不会判断 ASR 对不对，也不会自动查日期冲突；摘要质量取决于切块、提示词和底层模型。核心代码通常 MIT，但 integrations、embedding 模型和底层 LLM 逐项核对。

**适用判断**：长录音分层总结的工程骨架很实用；需要极简依赖或严格自研流程时，也可以只实现同样的 Map/Reduce 算法。

### 2.24 LangChain：通用链路编排

**项目类型**：通用 LLM/工具调用编排框架，不是 ASR、VAD 或摘要模型。

**能力清单**：

- 组合文档加载、切块、检索、模型调用、结构化输出和重试。
- 可表达 Stuff、Map-Reduce、Refine、检索增强和 agent 工作流。
- 便于替换 Qwen、Llama、Mistral 或远程模型，并统一回调和观测。

**局限和版本注意**：框架不会自动解决音频时间轴、partial/final、证据真实性或冲突；经典摘要 chain 在新版本可能处于弃用/迁移状态，使用前应锁定文档和版本。代码通常 MIT，provider integrations、模型权重和云服务条款另行审核。

**适用判断**：需要快速验证多模型组合、重试和观测时有价值；核心事实校验和时间戳映射仍应由明确的领域代码掌控。

### 2.25 BGE-M3：关键段落的多语言语义召回

**项目类型**：文本 embedding 模型，不是 ASR 或摘要模型。它把句段变成可比较的向量，适合在关键段落抽取前先做“哪些句子和主题最相关”的召回。

**能力清单**：

- 面向多语言语义检索，公开模型卡列出 100+ 语言和约 8192 token 上下文能力。
- 同时支持 dense vector、sparse lexical weight 和 multi-vector 表示，可做混合检索。
- 能按用户问题、主题词或历史摘要召回同义表达，例如“上线时间后移”和“交付日期调整”。
- 可把召回结果交给 cross-encoder 或 LLM 重排，再用 MMR 去重。

**实时性和资源**：embedding 通常比大语言模型便宜，但长句、批大小、向量库和索引更新会影响延迟。它只看文字；ASR 错字、时间戳缺失和句段切得不合理会直接影响召回。

**功能完整度**：适合做候选召回和语义去重，不负责音频、标点、说话人、事实核验或最终摘要。实际系统通常保留 BM25/关键词作为精确匹配基线，再和 BGE-M3 做 hybrid retrieval。

**商用核查**：`BAAI/bge-m3` Model Card 的模型许可标注为 MIT，官方 FlagEmbedding 实现也采用 MIT；量化/转换版本、底层 tokenizer、向量库和部署依赖仍要逐项核对。训练语料条款和部署数据隐私不能由 embedding 许可证代替。

**适用判断**：关键段落、按主题搜索和长录音证据召回很实用；只做短文本固定关键词时，BM25 可能更简单、更可解释。

**例子**：原文没有出现“延期”二字，但出现“上线时间要往后推”；BGE-M3 可以把它召回到“延期风险”问题下，随后由规则/LLM确认是否真的是风险。

### 2.26 Sentence-Transformers：召回后重排的通用工具

**项目类型**：embedding、semantic search 和 cross-encoder rerank 的模型/工具库，不是语音模型。典型做法是 bi-encoder 先从大量句段中高召回，再让 cross-encoder 对几十到几百个候选精排。

**能力清单**：

- 生成句向量、建立语义索引、按问题或主题检索句段。
- 使用 cross-encoder 同时读取“问题 + 候选句”，提升精排的语义判断。
- 支持批处理、GPU/CPU 和多种公开 embedding/reranker 模型。
- 可保留候选句的 `segment_id`，把检索分数和原文时间戳一起传给关键段落模块。

**实时性和资源**：bi-encoder 适合全量预计算；cross-encoder 只应处理小候选集，否则延迟和成本会快速上升。模型换语言或领域后，向量相似度分布会变化，阈值必须重新校准。

**功能完整度与商用核查**：它能把“召回 -> 重排”做成稳定组件，但不会识别音频、判断事实或生成摘要。官方 `sentence-transformers` 主库采用 Apache-2.0；具体 embedding/reranker 权重和 tokenizer 仍各有 Model Card 许可，商用要锁定实际模型和版本，不能把库许可证当成模型许可证。

**适用判断**：需要可解释、可替换的关键段落召回时很合适；不建议跳过候选证据，直接让 LLM 在整段长文本中凭感觉挑重点。

## 3. 从声音到文字：算法内部到底做了什么

### 3.1 采集和统一格式

大多数语音模型在内部希望看到类似下面的输入：

```text
PCM
采样率：16 kHz
声道：单声道
位深：16-bit
```

AAC、M4A、Opus 等压缩音频需要先解码。算法边界最好只解码一次，后续所有帧都使用同一采样时钟。墙上时钟可以漂移，样本序号和累计采样数更适合做精确时间轴。

预处理还可能包括重采样、双声道转单声道、音量归一化和轻度降噪。降噪不是越强越好：把风扇声压得太狠，可能连“s”“f”等辅音一起削掉，反而让识别更差。原始音频和处理后的音频最好都能追溯，便于定位是录音问题还是模型问题。

### 3.2 特征提取：模型不是直接看“声音曲线”

原始 PCM 通常会先按短时间窗口分帧，再经过频谱、filterbank 或 Mel 等特征提取；有些传统前端还会做预加重、窗函数和短时傅里叶变换，具体步骤由模型决定。可以把特征看成“每个时间点有哪些音高和能量”的图片。

```text
声音波形 -> 音频特征 -> 声学模型 -> token/字词
```

特征窗常见约 10~30 ms（例如 25 ms 窗、10 ms 步长），之后再聚合成更大的推理 chunk；具体数值由模型前端决定。帧越小，反馈更快但模型调用和调度开销更多；chunk 越大，上下文更充分但首字更慢。

### 3.3 VAD：先判断“有没有人说话”

VAD 是语音活动检测，不是转写。它通常输出每一帧的有声概率，再由状态机决定开始和结束。

```text
silence
  --连续有声--> speech
speech
  --短暂停顿--> speech（hangover，不立即切句）
speech
  --连续静音（时长按模型和噪声调参）--> endpoint
endpoint
  --提交句段--> silence
```

常见保护参数：

- **pre-roll**：检测到开口时，把前面约 100~300 ms 一起保留，避免吃掉第一个字；数值只是调参起点。
- **hangover**：短暂停顿不立即结束，避免“我们要 / 开始”被切成两句。
- **最大静音时长**：长时间没人说话时释放或重置 cache；保留、滚动还是重置由模型协议决定。

VAD 不应删除原始音频。它只是决定什么时候调用模型、什么时候形成句段。

### 3.4 声学模型和解码方式

常见模型路线可以这样理解：

| 路线 | 说明 | 优点 | 代价 |
| --- | --- | --- | --- |
| 自回归 encoder-decoder | 一次猜一个 token，猜完再猜下一个 | 上下文表达强，Whisper 属于此类 | 逐步生成，延迟和计算较高 |
| CTC | 每个时间位置先给标签，再去掉重复和空白 | 简单、低延迟、适合流式 | 长距离语言约束较弱，常需二次重排 |
| Transducer | 声音到来时边听边出字，内部维护状态 | 原生在线、延迟稳定 | 模型训练和部署较复杂 |
| 非自回归 | 一次估计一批 token 或隐藏表示 | 吞吐高，Paraformer 属于此类 | chunk/cache 和模型约束更严格 |

`beam search` 等解码策略会保留多个候选，不只看当前概率最高的一个字。它可能改善整体序列评分和准确率，但不保证专门减少同音字错误；候选越多，计算越慢。

### 3.5 cache：实时模型的“短期记忆”

cache 保存已经处理过的声学上下文、注意力状态或预测状态。它不是完整文字，也不能跨不同录音随意复用。

```text
新块 + 上一块 cache -> 新文字 + 新 cache
```

没有 cache 时，实时系统只能重复处理历史；错误的 cache 生命周期则会把上一段录音的内容带到下一段。句段结束后，cache 是保留、滚动还是 reset，必须按具体模型的 flush 规则处理。

### 3.6 标点、数字和专有名词

ASR 原始输出可能是：

```text
我们下周一上午十点讨论百分之五的折扣方案
```

标点和规范化模块可以输出：

```text
我们下周一上午 10:00 讨论 5% 的折扣方案。
```

实时阶段只做轻量处理，句段 final 后再做完整标点和格式化。原始文字必须保留，因为规范化可能改错数字或专有名词。

领域词或热词（人名、产品名、型号）可以在解码时提高指定候选的分数。例如把“Paraformer”加入词表，模型更不容易写成同音的普通词。热词只是偏置，不能把错误读音强行改成指定词；仍应保留原始输出和置信度，并用测试音频验证误替换是否增加。

### 3.7 partial/final 的稳定化算法

对原生 streaming 模型，通常由模型 endpoint 机制决定 final。对滑窗 Whisper，可以维护最近 2~3 次、已经按 token/词对齐并去掉已确认前缀的假设，求未提交部分的稳定公共前缀：

```text
confirmed = 对齐后的未提交假设的稳定公共前缀
partial   = 当前假设去掉已有 confirmed 后的尾部
```

每个句段应有 `segment_id` 和 `revision`。`revision` 变大表示同一句的新版本；收到 final 后在本次会话内冻结，不能再追加同一段全文。直接对未对齐的原始字符串求 LCP，遇到插入、删除或标点变化可能过早提交或漏字。

值得测的两个量：

- `revision_rate = 被修改的字符数 / 总字符数`
- `stable_latency = 最后一次修改到冻结的时间`

### 3.8 停止和尾部 flush

最后一句往往没有自然的长静音。停止信号到来时，算法应：

1. 把已收到但还没处理的音频送入模型。
2. 使用 `is_final` 或等价 endpoint 强制结束 VAD。
3. 进行尾部解码或 flush；只有模型给出可确认的最终文本时，才把最后的 partial 提交为 final，否则保留“未确认/识别失败”状态。
4. 只有所有尾部文字确认后，才报告转写完成。

直接关闭模型或连接，最容易丢掉最后半句。

### 3.9 两遍识别：先快后准

很多高质量系统不会强迫同一个模型同时满足“马上出字”和“全文最准确”：

1. **第一遍**用流式模型边听边出 partial/final，提供及时但可修订的文字。
2. **第二遍**在录音结束后用完整音频和更强的离线模型重跑，利用完整上下文、全局说话人和更细时间对齐。
3. 按时间范围或句段 ID 把第二遍结果映射回第一遍，替换文字、时间戳和关键段落证据。

**例子**：第一遍把“周三前”听成“周四前”，临时结果先显示“周四前”；第二遍利用完整上下文后改成“周三前”，摘要也只能引用第二遍的原文和时间。第一遍提供低延迟反馈，第二遍提供可核对的精修结果。

## 4. 时间戳和说话人算法

### 4.1 时间戳从哪里来

时间戳可以来自三种层次：

1. **句段级**：整句的开始和结束，实时最容易得到。
2. **词级/字级**：通过模型 token 时间或强制对齐得到，录后更准。
3. **音素级**：更细，但计算和模型依赖更多。

时间戳应该绑定原始样本位置，而不是只绑定处理或到达时间。音频缺口要明确标记，否则文字和声音会错位。

### 4.2 说话人分离（diarization）

说话人分离回答的是“什么时候是谁在说话”，不等于识别真实姓名。常见步骤：

```text
VAD 切语音段
 -> 提取每段 speaker embedding
 -> 按相似度聚类
 -> 输出 SPEAKER_00、SPEAKER_01 ...
```

**例子**：

```text
[00:00~00:05] SPEAKER_00：我们先看预算。
[00:05~00:08] SPEAKER_01：我同意这个方向。
```

实时阶段说话人标签可能暂时变化；录音结束后有全局上下文，聚类通常更稳定。除非有注册声纹和明确授权，否则 `SPEAKER_00` 不能直接显示成某个人的姓名。

多人同时说话时，单通道录音可能把两个人的字混在一起，或者只识别出声音较大的那个人。语音分离或多麦克风能改善这种情况，但会增加模型、算力和调参成本；不能只靠 VAD 或标点解决抢话问题。

## 5. 关键段落是怎么挑出来的

### 5.1 三种做法

| 方法 | 做法 | 优点 | 问题 |
| --- | --- | --- | --- |
| 抽取式 | 直接从原文挑句子/句段 | 可追溯，几乎不凭空造事实 | 语言可能不够顺 |
| 抽象式 | 让 LLM 重写和概括 | 表达自然、压缩率高 | 可能遗漏或编造 |
| 混合式 | 先抽取候选，再让模型排序/短改写 | 兼顾证据和可读性 | 流程较复杂，需保存映射 |

需要逐句核验的长语音和高风险文本，优先混合式。

### 5.2 第一步：按句段生成候选

候选不要来自 partial，要来自 final 句段。每个句段至少保存：

```json
{
  "segment_id": "seg_42",
  "start_ms": 18400,
  "end_ms": 22100,
  "speaker": "SPEAKER_01",
  "raw_text": "那我们下周一把报价单发给客户",
  "normalized_text": "那我们下周一把报价单发给客户。"
}
```

相邻且间隔很短的高分句可以合并成 15~60 秒的关键片段，避免只截出一句没有上下文的话。

### 5.3 第二步：中心性、关键词和新颖性打分

#### TextRank/中心性

把每个句子看成图中的一个节点，句子之间越相似，连线越强；连接很多重要句子的节点，中心性更高。它适合找“本段在讲什么”。

#### 向量中心性

把句子变成 embedding，计算它和本段平均向量的相似度。它比关键词更能识别同义表达，例如“交付日期需要调整”和“上线时间要往后推”可能被判为同一主题。

#### 规则信号

提高以下内容的召回率：

- 决策：确定、同意、定为、采用、取消。
- 待办：负责、安排、提交、发送、跟进、截止。
- 风险：问题、风险、阻塞、依赖、可能延期。
- 事实：金额、日期、数量、版本、人名、产品名。
- 问题：为什么、是否、待确认、需要谁批准。

#### 新颖性和 MMR

只按相关性排序会选出五句几乎一样的话。MMR 在选新句时同时惩罚和已选句子的相似度：

```text
MMR = 相关性 - λ * 与已选内容的最大相似度
```

`λ` 越大，越重视不重复；越小，越重视相关性。

一个可以开始做实验的“重要性”分数（上线前必须用标注集校准）是：

```text
score = 0.35 * 中心性
      + 0.25 * 新颖性
      + 0.25 * 决策/待办信号
      + 0.15 * 实体/数字信号
```

ASR 置信度不应直接当成“重要性”主分：它只说明模型对这段声音有多确定，不说明这件事在现实中一定是真的。可以把经过校准的 ASR 置信度另存为“证据可靠性”，用于人工复核排序。

### 5.4 第三步：受约束的 LLM 重排

让 LLM 只做三件事：

1. 在候选 `segment_id` 中选出最重要的片段。
2. 分类为 `decision`、`action_item`、`risk`、`question`、`fact` 或 `topic`。
3. 生成短标题和可读的规范化文本。

它不能自己发明候选时间、负责人、日期或数字。建议结果：

```json
{
  "type": "action_item",
  "title": "发送报价单",
  "quote": "那我们下周一把报价单发给客户",
  "normalized_text": "下周一发送报价单给客户。",
  "evidence_segment_ids": ["seg_42"],
  "start_ms": 18400,
  "end_ms": 22100,
  "selection_confidence": 0.86
}
```

必须同时保留 `quote`、`normalized_text` 和 `evidence_segment_ids`。整理后的文本可读，核验时仍能回指原句和原音频。
示例里的 `selection_confidence` 只是排序启发式分数；没有标注集校准时，不应把它当成概率，更不能当成事实真实性。
模型返回的 `evidence_segment_ids` 还必须经过候选白名单校验；只接受本次输入中真实存在的句段 ID，候选集之外的 ID 直接判为无效。

### 5.5 一个完整的关键段落例子

原始转写：

```text
00:02:10 甲：这个版本的问题是登录功能还不稳定。
00:02:17 乙：那先不要周五发布，改到下周一。
00:02:24 甲：可以，我今天把错误日志整理给技术团队。
00:02:31 丙：如果周一还没修好，客户演示要准备备用环境。
```

抽取结果：

```text
决策：发布日期从周五改为下周一（02:17~02:24）
待办：甲今天整理错误日志给技术团队（02:24~02:31）
风险：若问题未修复，需要准备客户演示备用环境（02:31~02:38）
```

注意，关键段落模块没有创造新的事实，只是把原文中已经出现的决定、待办和风险分出来。

## 6. 长录音总结算法

### 6.1 为什么不能一次总结 30 分钟原文

一次性输入全文会有四个问题：

1. 超过模型上下文限制。
2. 输入太长，成本和等待时间高。
3. 重要内容被平均稀释，模型抓不住决定和待办。
4. 一次失败后很难只重算局部。

所以通常使用分层总结。

### 6.2 四种常见总结模式

| 模式 | 说明 | 适用情况 | 风险 |
| --- | --- | --- | --- |
| Stuff | 全文一次塞给模型 | 短文本 | 超上下文，重点容易丢 |
| Map-Reduce | 每块先小结，再合并小结 | 长文本和批处理 | 合并阶段可能丢细节 |
| Refine | 第一块先写答案，后面逐块修订 | 需要顺序累积 | 后面内容可能覆盖前面结论 |
| Tree/Hierarchical | 小块 -> 中块 -> 总体，递归向上合并 | 很长文本和多主题 | 层数多，调试较复杂 |

LlamaIndex 的 TreeSummarize、LangChain 的 map-reduce/refine 都可以表达这些算法；框架只是编排，事实核验仍由规则层负责。

### 6.3 Map 阶段：每块只提取事实

切块时按句段和主题边界切，不要在一句话中间截断。可以先按 2~5 分钟或 1.5~3k token 做初始块，再用主题变化调整边界，保留约 10%~15% 重叠。

每块输出固定 JSON：

```json
{
  "chunk_summary": "本段讨论发布时间和发布风险。",
  "facts": [
    {"text": "登录功能仍不稳定", "source_segment_ids": ["seg_10"]}
  ],
  "decisions": [
    {"text": "发布日期改为下周一", "source_segment_ids": ["seg_11"]}
  ],
  "action_items": [
    {"task": "整理错误日志", "owner": "甲", "deadline": "今天", "source_segment_ids": ["seg_12"]}
  ],
  "risks": [],
  "open_questions": []
}
```

未知负责人和日期填 `null` 或“未提及”，不要猜。

### 6.4 Reduce 阶段：合并、去重和查冲突

Reduce 不是简单把几段摘要拼起来，而是要做四件事：

1. 合并同义内容，例如“周五发布”和“本周五上线”只保留一个主题。
2. 合并同一待办的负责人和截止时间。
3. 检查数字、日期、版本和立场是否矛盾。
4. 确认每条结论仍有来源句段。

**冲突例子**：

```text
甲：预算是 50 万。
乙：刚确认预算只有 30 万。
```

正确输出是“预算存在 50 万/30 万两种说法，待确认”，并附两处证据；不能让模型自作主张选 30 万。

### 6.5 最终展示层

最后一次模型调用只负责把已核对的结构化事实排成可读格式，例如：

```markdown
## 长语音摘要
本次讨论确定将发布日期调整到下周一，原因是登录功能仍不稳定。

## 已确定事项
- 发布日期：下周一（原音频 02:17~02:24）

## 待办
- 甲：今天整理错误日志给技术团队（02:24~02:31）

## 风险
- 若问题未修复，需要准备客户演示备用环境（02:31~02:38）

## 待确认
- 预算为 30 万还是 50 万。
```

Markdown 只是展示格式；内部仍应保留 JSON、来源 ID、时间戳、模型版本和转写版本 hash。

### 6.6 增量总结

实时总结不应每来一帧音频就调用 LLM。常见做法是：

```text
累计若干 final 句或 2~5 分钟
 -> 生成一个增量小结
 -> 与上一个小结合并
 -> 录音结束后再跑一次全局总结
```

增量小结是草稿，可能随着后文出现而改变；最终总结必须重新检查全局重复和冲突。

## 7. 情绪、事件和意图能力

这些能力不是“转写准确率”的同义词：

- **情绪**：高兴、平静、悲伤等模型标签，受语气、文化和数据偏差影响。
- **音频事件**：笑声、掌声、咳嗽、音乐、警报等非语言声音。
- **意图/主题**：这句话是在提问、下决定、抱怨还是安排任务。

推荐顺序是先完成可靠 ASR，再在有时间戳的句段上做分类。不要把情绪标签当成事实，也不要用一段低置信度转写直接推断人的真实意图。

## 8. 算法能力怎样评估

### 8.1 转写指标

| 指标 | 说明 | 直观理解 |
| --- | --- | --- |
| CER | 字符错误率 | 中文漏字、错字、替换多少 |
| WER | 词错误率 | 英文或分词语言更常用 |
| 首个 partial 延迟 | 开始说话到出现草稿 | 从起声到出现第一段文字的时长 |
| final 延迟 | 停顿到句段盖章 | 从端点到冻结结果的时长 |
| RTF | 处理秒数 / 音频秒数 | 通常要小于 1，再结合采集、排队、传输和稳定化后的端到端延迟验收 |
| revision rate | 被回改的文字比例 | 字幕跳动是否严重 |

### 8.2 时间戳、说话人和关键段落

- 时间戳：用时间区间 IoU 衡量预测和标注重叠程度。
- 说话人：用 DER 等指标衡量漏检、误分和错分说话人。
- 关键段落：Precision/Recall@K、冗余率、证据引用准确率、人工有用度。
- 摘要：事实一致性、幻觉率、决策/待办覆盖率、引用可回跳率。

ROUGE、BERTScore 等可以辅助比较文字相似度；BLEU 更常用于机器翻译，不能替代摘要事实核验。摘要写得像参考答案，不代表它没有编造事实。

### 8.3 推荐测试集

至少覆盖：安静近讲、远场、键盘噪声、多人重叠、口音、快速讲话、中英夹杂、数字和专有名词、长停顿、30 分钟长录音。所有模型必须使用同一音频、同一解码器和同一评估脚本，不能拿不同条件下的宣传数字直接比较。

## 9. 如何按需求选算法

| 需求 | 首选 | 备选 | 关键取舍 |
| --- | --- | --- | --- |
| 中文实时字幕 | Paraformer streaming + FSMN-VAD + 标点 | WeNet、sherpa-onnx 中文模型 | 延迟、中文 CER、部署复杂度 |
| 多语言实时 | SenseVoice、Qwen3-ASR | Vosk、sherpa-onnx 多语模型 | 语言覆盖和流式实现支持 |
| 录后高质量候选 | Whisper large + faster-whisper + WhisperX | FunASR 离线模型 | 速度、显存、词级对齐和说话人，必须在目标数据上实测 |
| 低配离线 | Vosk、sherpa-onnx、whisper.cpp | Moonshine | 内存、功耗与准确率 |
| 情绪/音频事件 | SenseVoice + 独立分类器 | 其他多任务模型 | 标签稳定性和误报 |
| 关键段落 | TextRank/embedding + MMR + 受约束 LLM | 纯 LLM 抽取 | 可追溯性优先 |
| 30 分钟以上总结 | Map-Reduce 或 Tree/Hierarchical + Qwen3 | Refine | 成本、上下文和冲突处理 |

通常的组合是：**一个实时 ASR + 一个录后精修 ASR + 一个总结模型**。没有必要强迫一个模型同时负责识别、对齐、说话人和总结。

## 10. 最容易犯的错误

1. 把 M4A 字节切片当成音频帧。
2. 用离线 Whisper 每秒从头重算，却称为真流式。
3. 把 partial 全文不断追加，造成重复字幕。
4. 只用固定分钟切块，把一个决定拆到两个摘要块里。
5. 让 LLM 自己生成时间戳、负责人和数字，没有原文证据。
6. 把 ASR confidence 当成事实真实性。
7. 认为有了 VAD 就自动有了转写。
8. 认为有了 WhisperX 就自动拥有注册说话人身份。
9. 每个音频帧调用一次总结模型，导致成本和延迟失控。
10. 只看 Star 或宣传速度，不在目标语言、噪声和目标环境上测 CER、RTF 和稳定延迟。

## 11. 开源许可与商用核查

“开源”不是一个单一结论。一个可交付的语音算法组合，至少要把代码、模型权重、第三方依赖和训练数据分开核对；四层中任何一层有额外限制，都会影响整体的使用、修改或再分发。

### 11.1 四层核查口径

1. **代码许可证**：查看仓库根目录的 `LICENSE`、子目录许可证和 `NOTICE`。MIT、Apache-2.0、BSD 等通常允许修改和商用，但仍要保留版权和免责声明；Apache-2.0 还涉及专利授权和修改标记。
2. **模型权重许可证**：权重不一定跟代码同一个许可证。以 Model Card、权重目录中的声明和下载页面为准，记录模型 ID、revision、文件哈希、是否 gated，以及是否允许商用、微调和再分发。转换、量化、导出 ONNX 或 GGUF 不会自动消除原权重的限制。
3. **第三方依赖**：运行时、tokenizer、分词器、VAD、对齐器、说话人模型、CUDA/ONNX Runtime 和向量库都要单独列出。一个 MIT 的上层库，不能覆盖它调用的 GPL、CC-BY、非商业或 gated 资产。
4. **训练数据和隐私**：开放权重不等于训练数据可以自由复制。核对数据集的商用、归因、隐私和地域要求；同时确认输入音频、转写文本和声纹向量是否会被发送到远程模型或写入日志。

### 11.2 主要项目核查表

| 组件 | 代码/运行库 | 权重或模型资产 | 商用核查重点 |
| --- | --- | --- | --- |
| Whisper、whisper.cpp、faster-whisper | 相关仓库代码通常为 MIT | 官方 Whisper 与转换/量化文件按来源确认 | 固定模型来源和 revision；转换格式不改变原权重义务 |
| FunASR、Paraformer | FunASR 工具箱代码为 MIT | 各 checkpoint 可能有独立 `MODEL_LICENSE` 或 Model Card | 逐个保存 checkpoint 条款、署名要求和衍生模型限制 |
| SenseVoice | 代码仓库通常为 MIT | SenseVoiceSmall 等权重按具体模型卡核对 | 不把工具箱代码许可当成多任务权重许可 |
| Vosk | API 常见为 Apache-2.0 | 语言模型、词典和社区重打包模型许可不统一 | 锁定实际语言模型；跨语言替换时重新审核 |
| sherpa-onnx | runtime 通常为 Apache-2.0 | model zoo 按模型包来源，可能是 Apache、CC-BY 或其他条款 | runtime 和每个模型包分别附许可证与哈希 |
| WhisperX、pyannote.audio | WhisperX 代码为 BSD-2-Clause；pyannote 代码为 MIT | 对齐模型、Whisper 权重和 pyannote pipeline 各自核对；部分 speaker 模型 gated 且标注 CC-BY-4.0 | 接受模型页条款并保留归因文本，核对词典和说话人数据授权 |
| Moonshine | 运行库和新模型按版本核对 | streaming/English 与 legacy 模型可能适用不同许可 | 不能用当前代码许可证推断旧模型或非英语模型 |
| WeNet、NVIDIA NeMo Speech | 代码通常为 Apache-2.0 | 预训练权重、容器、数据集和 CUDA 依赖分别核对 | 训练数据可用不等于权重可再分发，固定镜像和模型版本 |
| Qwen3、Qwen3-ASR、Qwen3-ForcedAligner | 代码和推理包按仓库许可证核对 | Qwen3 权重及 ASR/ForcedAligner 权重以各自 Model Card 为准 | 量化文件、vLLM、FlashAttention、tokenizer 和分词依赖单独记录 |
| BGE-M3、FlagEmbedding | 实现和当前 BGE-M3 资料通常标注 MIT | 模型卡和量化版本分别确认 | 混合检索依赖的 tokenizer、向量库和数据集另行核查 |
| Sentence-Transformers | 主库采用 Apache-2.0 | embedding、reranker 和 tokenizer 各自有 Model Card | 不把库许可延伸到第三方模型权重 |
| LlamaIndex、LangChain | 核心代码通常为 MIT | integrations、provider 和底层模型各自核对 | 它们是编排库，不会改变底层 ASR/LLM 的许可证 |

表中的“通常”只表示仓库的常见状态，不是对某个文件的法律结论。发布前应以锁定版本中的许可证文本为准；同一项目不同分支、模型别名和镜像文件可能有不同条款。

### 11.3 逐项核查步骤

1. 固定仓库 commit、模型 `repo/model_id`、revision 和 SHA-256，避免同名模型在不同时间被替换。
2. 同时保存代码许可证、权重 Model Card、`NOTICE`、`MODEL_LICENSE` 和下载页面快照，记录是否需要登录或接受额外条款。
3. 展开依赖树，至少标注 ASR、VAD、对齐、说话人、tokenizer、编解码器、推理 runtime 和 GPU 加速库的许可证。
4. 核对训练数据和评测数据的商用、归因、隐私、地域及再分发条件；不能因为模型输出可读就推断数据权利完整。
5. 明确允许的动作：内部使用、商业推理、微调、权重再分发、转换格式再分发和输出内容商用。任何一项没有明确依据，都标记为“待确认”。
6. 对 gated 模型记录申请账号、接受的条款和访问范围；对远程模型记录数据是否离开本地、保留多久以及是否用于再训练。

### 11.4 建议维护的准入记录

```text
component
repo_or_model_id
revision_or_commit
sha256
code_license
weight_license
third_party_and_data_license
commercial_use / fine_tune / redistribution
attribution_text
gated_terms
data_egress_and_retention
review_owner / review_date
```

只有当这张记录中的关键字段都有来源，且目标语言、噪声和推理环境的评测已经完成，才适合把算法组合标为“可用”。许可证通过不代表准确率通过；准确率、延迟和时间对齐仍要按本文的评测章节单独验收。

## 12. 可直接引用的关键段落

**关于实时转写：** 实时语音转写不是把长录音随便切成许多文件，而是把连续、可解码的音频按时间帧输入模型，并保留模型的上下文 cache。模型先给出可修改的 partial，经过稳定前缀、VAD 端点或模型 endpoint 确认后，再提交 final。结果消费层应按句段 ID 和版本更新，不能把每次返回的全文直接追加。

**关于 Whisper：** Whisper 是高质量的多语言通用 ASR 基座，典型做法是在约 30 秒 log-Mel 窗口上进行 Transformer encoder-decoder 自回归解码。它原生更偏离线，实时使用时需要滑窗、重叠、去重和 local agreement；faster-whisper 主要提升推理效率，并不会自动提供模型级连续状态和稳定输出规则。

**关于中文实时模型：** Paraformer streaming 的关键在于专用 streaming checkpoint、固定 chunk 和跨块 cache。它主要输入新增音频，同时按模型规则保留有限回看；句段结束时按模型规则 flush。离线 Paraformer 或其他离线模型不能只通过加一个 `cache` 参数就变成真正的流式模型。

**关于关键段落：** 关键段落应先从 final 句段中做抽取式召回，再用中心性、关键词、新颖性和 MMR 去重，最后让 LLM 在给定候选中做分类和短标题。每条结果都要保存原文摘录、来源句段 ID 和起止时间，以便回指原音频核验。

**关于长文本总结：** 长录音应按句段、主题和 token 上限分块，Map 阶段提取事实、决定、待办、风险和问题，Reduce 阶段去重并检查数字、日期和立场冲突，最后才生成展示稿。未知信息标记为未提及或待确认，不能让模型补猜。

**关于模型选择：** 没有一个 Star 最高的项目能包办所有任务。实时性、中文准确率、端侧资源、词级时间戳、说话人、情绪和总结是不同能力，应按测试集和目标平台组合选型。
